## §1 锚点与原则

### 1.1 5 部门 L1 平铺

Novel Writer 5 阶段在 Layout 顶部平铺为 5 个 L1 入口：

- **创意组**：灵感手记 / 外来参考 / AI 搜索 / 创意讨论 / 企划建议书（5 Tab，**VPS 缺 AI 搜索 tab，待补**）
- **企划课**：企划建议书 / 立项评估 / 作品设定中 / 已立项（4 Tab）
- **创作室**：单部作品写作 + 编辑器 + 参考侧栏
- **编审部**：AI 审查工具集（本文档）
- **文集库**：作品陈列 + 书评板块（详见 §8）

5 部门在"多部作品并发管理"视角下是**5 个平行的状态聚合**（每部门管自己的若干部作品），不是层级关系。任何部门降级为侧栏/面板的提议都先回到本原则反驳。

### 1.2 多部作品并发管理 = 设计判断锚点

**第一性问题**：5 部门 / 13 端点 / 状态值是否服务"多部作品并发管理"。

- 不是"单人线性流程是否太繁琐"
- 锚点用法：任何设计决策用"使用场景"做合理性测试，不用"形式感"做批评

### 1.3 编审部 L1 入口立场依据（R1/R2/R3）

**R1（功能独立性）**：编审部 = 自我审查 + 反复审看 + 找 bug + 保持前后一致，对应"责任编辑"角色。**注意**：这里的"责任编辑"是比喻，2.0+ 编审部不是流程卡点（详见 §3.4）。

**R2（与 5 部门 L1 平铺原则一致）**：编审部与其他 4 部门平级，是独立 L1 入口。

**R3（多部并发锚点）**：作者同时管多部作品时，编审部入口是"我手头 3 部待审稿挑哪部审"——与企划课的"挑哪部下周写"、创作室的"切到下一部正在写的"同构，是并发管理仪表盘的一个刻度。

## §2 1.0 vs 2.0+ 对照表

> 重要：本节避免后人误用 1.0 时代假设。详见 `memory/feedback_no_v1_contamination.md`。

| 维度 | 1.0 旧设计（已废弃） | 2.0+ 新设计（Day 2 锁定） |
|------|-------------------|-------------------------|
| 审阅粒度 | 章节级（每章完成前审） | 全文级（整部作品审） |
| 审阅主体 | 自我审稿（用户 = 责任编辑） | AI 审查官（用户 = prompt 配置 + 报告阅读） |
| 流程位置 | 强制节点（不审不能进下一章） | 可选异步（不卡文集库提交） |
| 触发方式 | 章节完成时自动 | 用户主动 / AI 异步 / 提交前可选 |
| 结果处置 | 通过/打回（决定能否继续） | 报告/标注（仅供参考） |
| 工具形态 | 编辑器内嵌审阅模式 | 独立 L1 工具集 + prompt 库 |

**关键**：2.0+ 编审部 = 全新职能，**与 1.0 章节审阅无关**。

## §3 2.0+ 编审部 4 核心特征

### 3.1 审阅对象：整部作品全文

- **不分章节**（无章节级审阅模块）
- **不设置章节级状态机**（无 chapter-level reviewing/reviewed 字段）
- 阅读体验：保留章节导航（章纲跳转），但审阅对象是"整部作品"

### 3.2 审阅动作：只读浏览

- **不进入作品内部修改**（不在编审部编辑）
- 审阅发现的问题可以**呈现提出**（如"逻辑漏洞在第 3 章"），但**不**作为卡点
- 即便发现问题，**不能阻止提交到文集库**

### 3.3 审阅主体：AI 审查官为主，用户为辅

- **AI 审查官**：异步跑 prompt，生成审阅报告
- **用户角色**：
  - Prompt 配置员（管理 prompt 库）
  - 报告阅读者（查看审阅结果）
- **不**邀请他人审稿（潜在 v5+ 议题，不在 Day 2 范围）

### 3.4 审阅结果：非卡点

- 审阅报告 = 体检报告（类似 CI 跑 lint，报告问题但**不**阻止 merge）
- 不改变 Project.status
- 不影响提交文集库流程
- 用户可基于报告决定是否返工（但不强制）

## §4 7 议题方向

### 议题 1：编审部 L1 主视图 = 审阅任务队列

- **设计**：多部作品 × 多次 AI 审阅报告的列表视图
- **多部并发视角**：作者同时管 3 部作品时，主视图是"挑哪部审"的仪表盘
- **与企划课 4 Tab 同构**（不是下拉，是顶部平铺的审阅任务列表）

### 议题 2：全文阅读器

- **设计**：跨章节连续阅读 + 进度跟踪
- **不分章节状态机**，但保留章节锚点跳转（点击章纲跳到对应位置）
- **进度存储**：后端存储（多设备同步是 2.0+ 默认，倾向后端）

### 议题 3：Prompt 库

- **默认 5 类 prompt**（对应 §5 评分卡 5 维）：
  - 情节：评估故事架构、节奏、张力释放
  - 人物：评估人物塑造、动机可信度、关系演变
  - 对话：评估对话是否符合人物、是否推进剧情
  - 逻辑：评估情节逻辑、设定一致性、时间线
  - 写作风格：评估文笔、风格统一、阅读体验
- **自定义增删**：用户可增删 prompt 类目
- **多 prompt 组合跑审阅**：一次审阅可组合多个 prompt

### 议题 4：作品级 snapshot

- **设计**：整部作品保存 1 个 snapshot（不分章节）
- **保留策略**：最近 20 个
- **Diff 视图**：A vs B 全文 diff（GitHub PR 风格）
- **触发**：每次保存自动 + 手动指定基线

### 议题 5：AI 审查触发机制

**3 种触发方式**：
- **A 用户主动**：点按钮触发（如"跑一次全面审查"）
- **B 异步**：用户提交审阅后，AI 后台跑（不阻塞 UI）
- **C 提交前可选体检**：提交到文集库前，弹窗问"是否先跑 AI 体检？"，跑完不卡提交

**3 种触发可组合**：用户主动 + 异步（默认）+ 提交前提示

### 议题 6：审阅报告形态（已细化，见 §5）

- 全文标注（问题点定位在原文位置）
- 摘要报告（总评）
- 评分卡（5 维打分，见 §5）
- **三视图并存**

### 议题 7：书评板块（放文集库，详见 §8）

## §5 评分卡 5 维定义

### 5.1 5 维（默认；可自定义）

| 维度 | 关注点 | 默认 Prompt 主题 |
|------|--------|------------------|
| 情节 | 主线清晰度 / 节奏 / 起承转合 | 评估故事架构、节奏、张力释放 |
| 人物 | 主角动机 / 配角立体 / 关系网 | 评估人物塑造、动机可信度、关系演变 |
| 对话 | 性格化 / 推进剧情 / 信息密度 | 评估对话是否符合人物、是否推进剧情 |
| 逻辑 | 时间线 / 因果链 / 设定自洽 | 评估情节逻辑、设定一致性、时间线 |
| 写作风格 | 语言 / 节奏 / 调性统一 | 评估文笔、风格统一、阅读体验 |

### 5.2 每维打分形态

- **分数**：1~5 星（★）+ 数字（4/5）
- **简短评语**：AI 生成 1~2 句（如"主线清晰，但中段节奏略平"）
- **详细问题**：可展开（点击展开看具体段落位置 + 原文引用）

### 5.3 评分汇总

- **总分**：5 维求和 / 25
- **百分比**：（总分 / 25）× 100%
- **软阈值警告**：每维可设"关注阈值"（默认 3/5），低于阈值时该维标 ⚠️
- **不阻止提交**：软阈值仅提示，**不**阻止提交到文集库

### 5.4 评分卡示意

```
┌─────────────────────────────────────────┐
│ 📊 审阅评分卡（作品：《X》）            │
├─────────────────────────────────────────┤
│ 情节:    ★★★★☆ (4/5)  "主线清晰..."     │
│ 人物:    ★★★☆☆ (3/5)  "主角动机..."     │
│ 对话:    ★★★★★ (5/5)  "符合人物..."     │
│ 逻辑:    ★★☆☆☆ (2/5)  ⚠️ "中期时间线..."  │
│ 写作风格: ★★★★☆ (4/5)  "语言统一..."    │
├─────────────────────────────────────────┤
│ 总分: 18/25 (72%)                        │
│ ⚠️ 软阈值警告: 逻辑 < 3，建议关注         │
│ （不阻止提交到文集库）                    │
└─────────────────────────────────────────┘
```

### 5.5 用户可配置

- 5 维名称（可自定义增删类目）
- 每维阈值（默认 3/5）
- Prompt 内容（每维默认 prompt 可改）

## §8 书评板块（放文集库，不放编审部）

### 8.1 决定（用户 2026-06-05 拍板）

**书评 = 放文集库**，不放编审部。

### 8.2 理由 3 条

1. **视角差异**：编审部 = 内部 AI 工具（"找 bug"），文集库 = 外部展示（"给读者看"）。书评是**面向读者**的推荐语，与编审部"AI 体检"视角不同
2. **流程位置**：编审部在创作室→文集库**之间**（可选体检），书评在文集库**内部**（作品陈列时的推荐语）。书评与作品一起被读者看到，与编审部"审完即弃"的工具属性不同
3. **不混淆内部/外部**：编审部报告 = 作者私人文档（AI 体检结果），书评 = 公开内容（类似豆瓣短评）。混在一起会让"哪些是 AI 写的、哪些是给读者看的"语义不清

### 8.3 详细设计（待 Day 3+ 展开）

- 书评生成：可用 prompt 生成（与编审部共享 prompt 基础设施，但**单独**的 prompt 类目）
- 书评展示：在文集库每部作品下显示
- 书评与编审部评分卡的关系：书评 = "推荐给读者的话"（外部），评分卡 = "AI 体检报告"（内部），两者不互通

## §10 沉淀（可推广设计模式）

本节给未来类似"工具型 L1 入口"设计提供参考。

### 10.1 "AI 体检报告"模式

- **适用场景**：用户对自己作品进行非阻塞质量检测
- **核心特征**：只读浏览 + AI 异步跑 + 报告/标注 + 非卡点
- **与"卡点流程"对比**：传统审稿是"必经节点"，AI 体检是"可选工具"，后者更适合个人创作者

### 10.2 "5 部门 L1 平铺"模式

- **适用场景**：多功能并行管理（个人/小团队工作流）
- **核心特征**：5 个平级入口 + 多部作品并发管理 + 不层级化
- **与"线性流程"对比**：线性流程是"一个人从头到尾走一遍"，平铺是"一个人同时管多部作品"

### 10.3 "Prompt 库驱动"模式

- **适用场景**：AI 工具集需要可配置性
- **核心特征**：默认 prompt 模板 + 自定义增删 + 多 prompt 组合 + 用户配置
- **价值**：把"AI 行为"从硬编码变成"用户可配置项"
