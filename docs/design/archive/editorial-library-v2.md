## §1 锚点与原则

### 1.1 5 部门 L1 平铺

Novel Writer 5 阶段在 Layout 顶部平铺为 5 个 L1 入口：

- **创意组**：灵感手记 / 外来参考 / AI 搜索 / 创意讨论 / 企划建议书（5 Tab，**VPS 缺 AI 搜索 tab，待补**）
- **企划课**：企划建议书 / 立项评估 / 作品设定中 / 已立项（4 Tab）
- **创作室**：单部作品写作 + 编辑器 + 参考侧栏
- **编审部**：AI 审查工具集（详见 editorial-dept-v2.md）
- **文集库**：作品陈列 + 书评板块（**本文档**）

5 部门在"多部作品并发管理"视角下是 **5 个平行的状态聚合**（每部门管自己的若干部作品），不是层级关系。

### 1.2 多部作品并发管理 = 设计判断锚点

**第一性问题**：5 部门 / 13 端点 / 状态值是否服务"多部作品并发管理"。

- 不是"单人线性流程是否太繁琐"
- 锚点用法：任何设计决策用"使用场景"做合理性测试，不用"形式感"做批评

### 1.3 文集库 L1 入口立场依据（R1/R2/R3）

**R1（功能独立性）**：文集库 = 私人归档工具，作者"完工后收纳"+"反复翻看"+"对内留念"。**注意**：这里的"归档"是**私人**含义，**不**是"对外发布"。

**R2（与 5 部门 L1 平铺原则一致）**：文集库与其他 4 部门平级，是独立 L1 入口。

**R3（多部并发锚点）**：作者同时管多部作品时，文集库入口是"我手头 5 部完工作品挑哪部翻看/挑哪部给书评"——与企划课的"挑哪部下周写"、创作室的"切到下一部正在写的"、编审部的"挑哪部审"同构。

## §2 1.0 vs 2.0+ 对照表

> 重要：本节避免后人误用 1.0 时代假设。详见 `memory/feedback_no_v1_contamination.md`。

| 维度 | 1.0 旧设计（已废弃） | 2.0+ 新设计（Day 2 锁定） |
|------|-------------------|-------------------------|
| 文集库定位 | 公开博客 / 出版平台 | **私人归档工具** |
| 作品可访问性 | 公开（任何读者可读） | 私人（仅作者本人） |
| "发布" 概念 | 必需（"发布"=作品上线） | **不**存在（"归档"=搬入文集库） |
| 书评读者 | 公开读者评论 | 作者私人留念（默认不外发） |
| 流量/读者画像 | 有（PV/UV/读者分布） | **不**存在（无外发则无流量概念） |
| 分享能力 | 支持（链接/嵌入） | **不**支持（无对外接口） |
| 工具形态 | 博客系统 + 评论系统 | Collection 扁平分组 + AI 书评 |

**关键**：2.0+ 文集库 = 私人归档，**与 1.0 公开博客/出版平台无关**。

### 2.1 1.0 已废弃假设清单

以下 1.0 时代假设在 2.0+ **不**适用，**禁止**在设计讨论中默认带上：

- ❌ "文集库 = 博客"（1.0 假设）
- ❌ "书评 = 公开读者评论"（1.0 假设）
- ❌ "作品可分享给他人"（1.0 假设）
- ❌ "文集库有 SEO/读者画像/订阅"（1.0 假设）
- ❌ "有'发布/草稿'二态"（1.0 假设，2.0+ 沿用 M1-A `archived` 终态）
- ❌ "文集库有公开/私密切换"（1.0 假设，2.0+ **永远**私人）

## §3 2.0+ 文集库 4 核心特征

### 3.1 工具定位：私人归档

- **纯私人**：仅作者本人可访问，**不**对外发布，**不**支持分享链接
- **归档语义**：作品完工后，从"创作室"（writing/written）流转到"文集库"（archived）
- **只读 + 可软删**：文集库内**不**编辑作品（详见 §3.2 / §4 议题 4），但**可**软删到文件暂存（详见 §4 议题 6）
- **与 1.0 公开博客区分**：1.0 文集库 = 公开发布平台；2.0+ 文集库 = 私人归档工具
- **没有"读者"概念**：作者翻看时 = 自己留念；不假设有第三方读者

### 3.2 流转节点：沿用 M1-A archived

- **进入文集库 = Project.status 变为 `archived`**
- **状态机退出文集库 = 不支持**（`archived` 是终态，无 `archived → writing` 之类回流，详见 §6.3）
- **文件暂存软删 = 唯一"离开文集库"路径**：`archived` Project 可软删（`deletedAt=now`）→ 文件暂存；restore 后回到 `archived`（详见 §4 议题 6 + §6.3）
- 与 1.0 "已发布/草稿" 二态无关，2.0+ = 沿用 M1-A 8 primary 字面量

### 3.3 作品陈列：Collection 扁平分组

- **Collection 模型**：纯容器，**无层级**（详见 §7）
- **1—N 关系**：一个 Project 可属于 1—N 个 Collection；一个 Collection 可包含 0—N 个 Project
- **支持空 Collection**（如"玄幻 - 备选"先建好等未来归档）
- **与 1.0 "专栏/分类树"区分**：1.0 = 层级分类；2.0+ = 扁平标签式分组

### 3.4 书评板块：AI 生成为主，作者留念

- **AI 书评生成**（与编审部共享 prompt 基础设施，**单独** prompt 类目）
- **作者手动编辑**（生成不满意可改）
- **私人可见**（默认仅作者本人，与文集库整体定位一致）
- **不模拟"读者视角"**：1.0 可能假设"AI 模拟读者写推荐语"，2.0+ = AI 帮作者提炼"我自己想留念的话"

## §4 5 议题方向

### 议题 1：文集库 L1 主视图 = 全部作品 + Collection 导航

- **设计**：默认进入"全部作品"网格/列表 + 左侧 Collection 导航栏
- **Collection 导航形态**：左侧侧栏（点击切换 Collection，0 Collection 时显示"全部作品"）
- **多部并发视角**：作者同时管 3 部完工作品时，主视图是"挑哪部翻看"的仪表盘
- **与企划课 4 Tab 同构**（顶部平铺 L1，不是下拉）

### 议题 2：作品详情页（陈列卡片 + 书评）

- **设计**：点击作品 → 详情页（封面 + 简介 + 元数据 + 书评 + Collection 归属）
- **只读浏览**：**不**进入编辑器（编辑器在创作室）
- **书评展示**：详情页底部独立板块
- **元数据展示**：title / author / coverImage / wordCount / status / createdAt（必显）+ tags / description / masterPrompt（可选）
- **不展示私人心流**：scraps（剪贴簿）/ timelineEntries / creativeFlows **不**在文集库展示（保留在创作室/编审部）

### 议题 3：Collection 管理

- **CRUD 5 端点**（沿用 2.0 TASK-018）：
  - GET /collections（列表）
  - GET /collections/:id（详情）
  - POST /collections（创建）
  - PUT /collections/:id（更新）
  - DELETE /collections/:id（删除）
- **删除语义**：仅删除 Collection 容器，**不**删作品（Project.relation 是 SetNull，作品 Project 仍可访问）
- **命名规则**：name 允许重名（区分靠 id，不强制 unique）

### 议题 4：归档触发

- **入口**：作品详情页（创作室）"归档到文集库"按钮
- **前置条件**：Project.status 必须是 `writing / written / reviewing / reviewed`（stage-guard 校验；**Day 2 移除 `shelved` 前置状态**）
- **状态流转**：`writing/written/reviewing/reviewed → archived`（5 桶 → archived 单点）
- **归档后**：
  - 作品从创作室列表消失
  - 出现在文集库列表
  - 编辑器**不**可访问（archived 终态，编辑需先恢复——但 M1-A 不支持 `archived → writing`，详见 §6.3）
  - 文集库详情页**只读浏览**（**不**编辑作品正文/章节）
  - 文集库详情页**可**软删到文件暂存（详见议题 6 / §6.3）
- **与"草稿保存"区分**：归档 ≠ 保存；归档 = 终态进入文集库

### 议题 5：与编审部的关系

- **编审部**：审阅工具集（生成审阅报告 / 评分卡）→ 报告留编审部
- **文集库**：陈列 + 书评（与作品一起被作者翻看）→ 书评留文集库
- **不互通**：编审部评分卡 ≠ 书评（详见 §5.4）
- **共享基础设施**：AI Provider / Prompt 库基础架构

### 议题 6：删除入口（→ 文件暂存）— Day 2 决议 方案 A

- **设计**：文集库详情页（议题 2 提到的页面）右上角加"🗑️ 删除"按钮，与其他 L1 删除按钮一致
- **触发**：点击 → 二次确认弹窗 → `POST /projects/:id/soft-delete` → `deletedAt=now`
- **归宿**：落入全局文件暂存（与其他状态软删一致，详见 `overall-architecture.md` §八 + [`file-staging-v2.md`](./file-staging-v2.md)）
- **文件暂存 restore 行为**：用户从文件暂存 restore → `deletedAt=null`，**status 保持 `archived`**（**不**流转到 writing/written）。即"文件暂存恢复后回到文集库原位置"
- **永久删除**：文件暂存中可二次确认物理删除（与其他文件暂存作品一致）
- **跨阶段不退回影响**：`archived → writing` 仍**不**支持（保持状态机纯净）。如果用户想"修正在文集库翻看时发现的错别字"，只能走"文件暂存 restore → 写完重归档"流程（详见 §6.3）
- **与 v4.1 §0 不变量一致**："任何状态都可'删除'到全局文件暂存"

### 议题 7（待定）：错别字修正流程

详见 §6.3 "archived 终态与软删的关系"。Day 2 不展开，**留作 M2+ 议题**（如"导出 → 修改 → 重新导入"，或"原地轻量编辑"等）。

## §5 书评板块详细设计

### 5.1 定位（用户 2026-06-05 拍板，Q4 选项 A）

- **AI 生成为主**：用户点"生成书评"按钮，AI 异步跑 prompt 生成
- **手动编辑**：生成不满意可手改
- **默认私人**：仅作者本人可见
- **与编审部共享 prompt 基础设施**（AI Provider / Prompt 库），**单独** prompt 类目

### 5.2 Prompt 类目（与编审部区分）

- **编审部 prompt**：5 维（情节/人物/对话/逻辑/写作风格）→ 评分卡
- **书评 prompt**：3 类（推荐语 / 卖点提炼 / 主题阐释）→ 短文

**默认 3 类书评 prompt**：

| 类型 | 字数 | 用途 |
|------|------|------|
| 推荐语 | 100—200 字 | "这本书讲了什么"（一句话讲清故事） |
| 卖点提炼 | 3—5 条 bullet | "为什么值得读"（亮点/差异点） |
| 主题阐释 | 200—400 字 | "作者想表达什么"（核心主题 + 思想深度） |

**自定义增删**：用户可增删书评类目（与编审部一样，详见 editorial-dept-v2.md §4 议题 3）。

### 5.3 生成流程

```
[作品详情页（文集库）] → [生成书评] 按钮
  → 弹出 prompt 选择（推荐语/卖点/主题）
  → 异步跑 AI（不阻塞 UI）
  → 生成结果展示在编辑框（可改）
  → 用户点保存 → 写入 Project.metadata._bookReview
```

**存储位置**：`Project.metadata._bookReview = { 推荐语: "...", 卖点: [...], 主题: "..." }`

### 5.4 书评与编审部关系

| 维度 | 编审部 | 文集库书评 |
|------|--------|------------|
| 视角 | 内部 AI 工具（"找 bug"） | 作品陈列（"翻看时看到"） |
| 读者 | 仅作者 | 仅作者 |
| 形态 | 评分卡 + 报告 | 短文 + bullet |
| Prompt 主题 | 5 维（情节/人物/对话/逻辑/风格） | 3 类（推荐/卖点/主题） |
| 触发 | 主动 / 异步 / 提交前提示 | 主动（用户点按钮） |
| 与作品关系 | 分离（独立报告） | 关联（写在 Project.metadata） |
| 存储 | Project.metadata._editorialReport | Project.metadata._bookReview |

**关键**：书评 ≠ 编审部报告。书评 = "翻看时给作者自己留念的话"；编审部报告 = "AI 体检结果"。两者**不**互通。

## §6 状态字面量集（M1-A 落地，Day 2 不动）

### 6.1 文集库与 Project.status 关系

**Q3 答案（用户 2026-06-05 拍板）**：**选项 A（沿用 M1-A archived）**

- M1-A 13 端点已落地 status 字段，**Day 2 不动**
- 文集库**只读** Project.status（不主动改 status）
- **进入文集库 = Project.status = `archived`**
- **状态机退出文集库 = 不支持**（`archived` 状态是终态，详见 §6.3）
- **文件暂存软删 = 唯一"离开文集库"路径**（详见 §4 议题 6）：
  - 软删：`POST /projects/:id/soft-delete`（文件暂存入口）→ `deletedAt=now`
  - restore：`POST /projects/:id/restore` → `deletedAt=null`，**status 保持 `archived`**
  - 物理删除：文件暂存中可二次确认 `DELETE /projects/:id`（与全局文件暂存规则一致）

### 6.2 Project 9 字面量（8 primary + 3 legacy read）

来源：`backend/src/constants/statuses.ts`

- **primary（8）**：`planning | planned | writing | written | reviewing | reviewed | archived`（**Day 2 移除 `shelved`**，详见 [`file-staging-v2.md`](./file-staging-v2.md) §2.2）
- **legacy read-only（3）**：`imported | draft | completed`（**新写入禁止**，只读映射用，详见 `intake-flow-v2.md`）

### 6.3 `archived` 状态语义

- **`archived` = 已归档**（作品完工后搬入文集库）
- **状态机不流转**：M1-A stage-guard 设计 `archived` 为终态，**不**支持 `archived → writing` 之类回流（保持状态机纯净 + 跨阶段不退回原则）
- **可软删到文件暂存**（**与"状态机不流转"不冲突**）：
  - 软删是**文件暂存机制**，**不**是状态机流转
  - 软删 = `Project.deletedAt = now`（文件暂存入口）
  - restore = `Project.deletedAt = null`，**status 保持 `archived`**（回到文集库原位置）
  - 这是 v4.1 §0 "任何状态都可'删除'到全局文件暂存" 在 `archived` 上的体现
- **永久删除**：文件暂存中可二次确认物理删除（与其他文件暂存作品一致）
- **错别字修正流程**（Day 2 决议 方案 A）：
  - 翻看时发现错别字 → **不**在文集库内编辑（保持只读 + 状态机纯净）
  - 走"文件暂存 restore → 写完重归档"流程（**不**支持"文集库 → 创作室"回流）
  - 实际操作：文件暂存 restore → 改 status（需要新端点，**M2+ 议题**）→ 修改 → 重新 archived
  - 实际 Day 2 实现：接受"归档前在创作室修正所有错别字"，归档后**不**提供修正流程
- **与 shelved 区分**：shelved **已废弃**（Day 2 方案 C 移除，详见 [`file-staging-v2.md`](./file-staging-v2.md) §2.2）。2.0+ = archived 终态 + 软删 only

### 6.4 常见误区澄清

- **`shelved` ≠ `archived`**：**已废弃**（Day 2 方案 C 移除 shelved 字面量，详见 [`file-staging-v2.md`](./file-staging-v2.md) §2.2）。2.0+ 状态机**不**再有 shelved，archived = 唯一"已停止流转"语义（终态 + 软删入口）
- **`imported` ≠ "已发布"**：`imported` 是 Project **legacy read-only** 字面量，语义是"1.0 时代从外界导入的草稿"（已废弃，详见 `intake-flow-v2.md`）
- **"已发布" 概念在 2.0+ 不存在**：1.0 时代可能有"已发布"状态，2.0+ 沿用 `archived`，**禁止**引入新字面量
- **`imported` 是 1.0 残留**：2.0+ 移除 `imported` Project 字面量（迁移到 `planning`），正确导入流程走 FileReference（创意组 外来参考），详见 [`intake-flow-v2.md`](./intake-flow-v2.md)
- **"草稿/公开" 二态在 2.0+ 不存在**：1.0 时代可能有"草稿"+"已发布"二态，2.0+ = 8 primary 字面量流转 + 终态归档
- **archived 终态 ≠ 不可删**：`archived` Project 仍**可**软删到文件暂存（文件暂存机制≠状态机流转）；但**不**支持 `archived → writing` 之类状态机回流

## §7 Collection 字段处理

### 7.1 Q2 答案（用户 2026-06-05 拍板）：**选项 A（扁平分组）**

- **Collection = 纯容器**（id / name / description / createdAt / updatedAt）
- **1—N 关系**：Project 可属于 1—N 个 Collection
- **无层级**（**禁止** Collection 嵌套 Collection）
- **支持空 Collection**（先建容器等未来归档）
- **与 1.0 "专栏/分类树"区分**：1.0 = 层级（玄幻 > 仙侠 > 修真）；2.0+ = 扁平标签

### 7.2 当前 schema 状态

来源：`backend/prisma/schema.prisma:17`

```
model Collection {
  id          String    @id @default(uuid())
  name        String
  description String?
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt
  projects    Project[]
}
```

当前为简单 string 字段，**Day 2 不动 schema**。

### 7.3 Collection 字段与文集库关系

- **Collection 不影响 Project.status**（Project.status 由端点流转决定，**不**由 Collection 归属决定）
- **删除 Collection 不删作品**（Project.relation 是 SetNull，详见 schema.prisma:60-61）
- **Collection 名称唯一性**：**不**强制（同名 Collection 允许，区分靠 id）
- **空 Collection 允许**：创建后可空着，等未来归档时再放作品
- **Collection 与 tags 关系**：Collection 是粗粒度分组，tags 是细粒度标记，两者互补

## §8 与编审部的关系

### 8.1 视角差异

- **编审部** = 内部 AI 工具（"找 bug / 体检"）
- **文集库** = 私人归档 + 留念（"翻看 + 自我欣赏"）
- **核心区分**：编审部 = 找问题；文集库 = 留念价值

### 8.2 流程位置

```
[创作室] → [可选：编审部体检] → [文集库归档]
   ↓              ↓                    ↓
writing     reviewing/reviewed      archived
   /written
```

- **编审部 = 可选**（不卡文集库提交）
- **文集库归档 = 终态**（`archived` 不可逆）
- **与 M1-A 13 端点关系**：`move-to-archive` 端点（在 M1-A 13 端点中）触发 archived

### 8.3 内容互通

- **编审部报告** = 体检结果（建议存储 `Project.metadata._editorialReport`）
- **书评** = 翻看时的话（存储 `Project.metadata._bookReview`）
- **不互通**：报告 ≠ 书评，作者翻看作品时只看书评
- **编审部报告归档后**：归档时**不**强制带编审部报告（即使有，也**不**显示在文集库详情页）

### 8.4 Prompt 基础设施共享

- **AI Provider 管理**：编审部 + 文集库共用（Day 3 议题）
- **Prompt 库**：**不**合并（编审部 5 维 prompt + 文集库 3 类 prompt，**单独**类目）
- **用户配置**：编审部阈值 / 文集库书评风格，可分别配置
- **存储位置**：建议统一存 `Project.metadata._prompts` 子树（待 Day 3 AI 策略细化）

## §10 沉淀（可推广设计模式）

### 10.1 "私人归档"模式

- **适用场景**：用户对自己作品进行非公开收藏 + 自我留念
- **核心特征**：纯私人 + 终态归档 + AI 辅助生成留念内容 + 扁平分组
- **与"博客平台"对比**：博客 = 对外发布 + 读者评论 + SEO；私人归档 = 自我留念 + AI 书评 + 无外发
- **价值**：把"个人创作工具"与"对外发布平台"彻底解耦，避免设计混淆

### 10.2 "5 部门 L1 平铺"模式

- **适用场景**：多功能并行管理（个人/小团队工作流）
- **核心特征**：5 个平级入口 + 多部作品并发管理 + 不层级化
- **与"线性流程"对比**：线性流程是"一个人从头到尾走一遍"，平铺是"一个人同时管多部作品"

### 10.3 "沿用既有状态机"模式

- **适用场景**：新功能不引入新状态字面量
- **核心特征**：M1-A 13 端点 + 9 primary 字面量已覆盖新功能需求 → **不**增量
- **价值**：避免状态机爆炸，保持后端状态机稳定

### 10.4 "AI 生成为主 + 手动编辑"模式

- **适用场景**：AI 辅助生成短文/卡片内容
- **核心特征**：默认 AI 生成 + 用户可改 + 异步跑 + 单独 prompt 类目
- **价值**：用户拿 AI 结果当起点，不满意可改，比"AI 一次性生成"灵活

### 10.5 "内部分组扁平化"模式

- **适用场景**：多对象需要分组，但**不**需要层级
- **核心特征**：纯容器 + 1—N 关系 + 允许空容器 + 不强制命名唯一
- **与"分类树"对比**：分类树 = 严格层级 + 路径语义；扁平分组 = 标签式聚合 + 自由组合
