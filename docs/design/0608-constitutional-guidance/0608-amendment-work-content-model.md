# 0608-amendment-work-content-model.md — Work 作品内容模型修正案

> **文档角色**：0608 宪法级指引的内容决策修正案。定义 novel-writer 的核心领域对象 Work（作品）、作品详情页起点、内容结构，以及 1.0 `Project` 语义遗留的治理路径。
> **优先级**：P0 — 所有作品详情页、内容编辑、字段命名、前后端类型和 API 语义治理必须遵循。
> **关系**：补充 `0608-amendment-decision-separation.md`；上位约束 `0608-ux-interaction-model.md`、`0608-status-context-labeling.md`、`0608-dept-workspace-model.md` 中涉及作品内容的部分。
> **状态**：Amendment v1.1（2026-06-11）

---

## §0 修正案摘要

0608 流程决策修正案已经明确：

> 内容变化不等于流程推进。

本修正案进一步明确“内容决策”的核心对象：

> novel-writer 的核心领域对象是 **Work（作品）**，不是 1.0 遗留的 `Project`。

`Project` 可以作为短期技术实现名、数据库表名、API 兼容名继续存在，但不得继续作为产品语义、设计文档和 UI 文案中的核心概念。

---

## §1 核心判断

### 1.1 Work 是领域对象

Work 表示一部正在构思、企划、创作、审阅或归档的作品。

Work 从“作品构思中”开始存在，不从 Project(planning) 或“接收入企划课”才开始存在。

因此：

- 作品不是立项后才有。
- 作品详情页不是 Project 详情页。
- 作品详情页的起点是创意组的“作品构思中”。
- Project 只是历史技术实现名，不再定义领域边界。

### 1.2 Project 是遗留技术名

1.0 时代的 `Project` 混合了承载对象、流程状态、作品字段、AI 字段、展示字段等多重语义。

在 0608 语义下，`Project` 存在以下问题：

- 容易暗示作品从“立项/企划”才开始。
- 容易把流程状态和内容实体混在一起。
- 容易让 `/work/:id` 与 `Project` API 两条线并行分裂。
- 容易污染作品元数据字段边界。

治理原则：

> 文档和 UI 先改成 Work 语义；代码和数据库分阶段兼容迁移；不做一枪式大重命名。

## §2 作品详情页起点

### 2.1 起点声明

作品详情页的起点是：

```text
创意组 → 创意作品 → 作品构思中（CreativeFlow）
```

而不是：

```text
企划课 → Project(planning)
```

### 2.2 各阶段内容开放

| 工作区状态 | Work 是否存在 | 详情页写入权限 | 说明 |
|-----------|--------------|---------------|------|
| 构思中 | 是 | 可写 | 创建和生长作品雏形 |
| 企划中 | 是 | 可写 | 规范化作品元数据和章节架构 |
| 创作中 | 是 | 可写 | 主要写入作品正文，元数据可补充 |
| 审阅中 | 是 | 可写 | 保存批注、审阅记录和修订建议 |
| 其他状态 | 是 | 默认只读 | 如需改内容，先由列表流程动作退回进行中态 |

## §3 作品详情页三分法

WorkDetailPage 统一由三部分组成：

```text
作品详情页（WorkDetailPage）
  ├─ 作品元数据
  ├─ 作品章节
  └─ 作品正文
```

### 3.0 作品详情页编辑态

作品详情页采用“只读参照态 → 显式编辑态”的双态模型。

默认进入作品详情页时，页面处于只读参照态：

- 展示作品元数据、作品章节、作品正文预览。
- 允许返回、切换 Tab、进入可读预览。
- 不直接启用字段编辑、章节编辑或正文编辑。
- 不出现任何流程推进按钮。

只有点击页面级强指令：

```text
编辑作品详情
```

后，作品详情页才进入内容编辑态。此时允许出现分区内容动作：

- 编辑作品元数据
- 编辑作品章节
- 编辑正文 / 进入正文编辑

页面级编辑态动作：

- 完成编辑
- 取消编辑

约束：

- “编辑作品详情”只是进入内容决策模式，不是流程决策。
- “完成编辑”表示结束本次详情页编辑会话，不等于作品流程完成。
- 若存在未保存修改，退出编辑态前必须提示用户保存或放弃。
- 不得用一个总保存按钮假装作品元数据、作品章节、作品正文是同一种内容结构。

### 3.1 分区保存确认

作品元数据、作品章节、作品正文属于不同内容样态，必须有各自的保存确认方式：

| 分区 | 编辑入口 | 保存确认 | 说明 |
|------|----------|----------|------|
| 作品元数据 | 编辑作品元数据 | 保存元数据 / 取消元数据修改 | 重点保护标题 + 作品梗概 |
| 作品章节 | 编辑作品章节 | 保存章节 / 取消章节修改 | 重点保护第几章 + 章节名 + 章节梗概 |
| 作品正文 | 编辑正文 / 进入正文编辑 | 按正文编辑器或章节正文保存机制确认 | 正文可按章节独立保存，不强塞进详情页总表单 |

页面级“完成编辑”只能在各分区修改已保存或已放弃后完成。

### 3.2 各阶段内容决策职责

| 阶段 | 主要任务 | 作品元数据 | 作品章节 | 作品正文 |
|------|---------|-----------|---------|---------|
| 创意组 / 构思中 | 形成作品雏形 | 标题 + 作品梗概必填；其他自由输入 | 可为空，可粗略记录 | 可为空，可存片段 |
| 企划课 / 企划中 | 完善作品规划 | 继承标题 + 作品梗概，重点丰富作品元数据 | 重点建立章节架构；第几章 + 章节名 + 章节梗概必填 | 通常不写正文 |
| 创作室 / 创作中 | 写成作品 | 可补充、修正、追加 | 可调整、补充 | 核心写入区，逐章成型 |
| 编审部 / 审阅中 | 审阅与修订判断 | 作为审阅依据，原则上不改 | 作为审阅依据，原则上不改 | 审阅、批注、修订建议 |
| 文集库 / 已归档 | 阅读与归档 | 隐藏 | 隐藏 | 只保留作品正文 |

阶段职责解释：

- 创意组回答：这是不是一部作品？
- 企划课回答：这部作品怎么写？
- 创作室回答：这部作品写出来了吗？
- 编审部回答：这部作品是否成立、是否需要修？
- 文集库回答：这部作品如何被阅读和保存？

### 3.3 作品元数据

作品元数据回答：

> 这部作品是什么？写作时应当记住什么？

它是写作时的创作参照面板，不是死板表单。

最低必填字段：

- 标题
- 作品梗概

候选选填字段需后续协商，不在本修正案中一次性锁死。候选包括：

- 题材 / 标签
- 核心主题
- 核心冲突
- 主角 / 主要人物
- 世界观 / 背景
- 叙事视角
- 写作风格
- 目标字数
- 灵感来源
- 不想写成什么样
- 追加设定 / 创作备注

约束：

- 标题和作品梗概是最高级必填字段。
- 其他字段允许为空，不阻塞早期构思。
- 元数据应尽量只增不减，核心字段修改需谨慎。
- 新想法优先追加到备注、补充设定或修订说明，而不是覆盖旧判断。

### 3.4 作品章节

作品章节回答：

> 这部作品如何展开？

最低必填字段：

- 第几章
- 章节名
- 章节梗概

候选选填字段：

- 本章目标
- 出场人物
- 场景地点
- 关键冲突
- 伏笔 / 回收
- 情绪节奏
- 备注

约束：

- 章节条目可以追加。
- 章节顺序可以调整。
- 章节名和章节梗概在企划中应逐步补齐。
- 创作中允许根据实际写作补充和调整章节设计。

### 3.5 作品正文

作品正文回答：

> 最终写出来的文本是什么？

约束：

- 正文属于最自由编辑层。
- 允许修改、删除、重写和打磨。
- 正文不适用“只增不减”原则。
- 章节正文保存不等于作品完成。

## §4 Project 遗留字段治理

本节服从 `0608-legacy-freeze-list.md` §0.1 的 Legacy 默认无效原则：

> 所有 1.0 术语、字段、组件、API、页面入口必须重新举证；不能证明符合 0608 宪法、流程/内容决策分离、Work 核心模型的，默认进入冻结、改名、迁移或删除候选。

因此，`Project`、`章节规划`、`章节管理` 等不得再作为产品语义自然继承，只能作为短期技术兼容名或迁移对象存在。

### 4.1 字段分流原则

所有 1.0 `Project` 字段必须重新归类：

| 归类 | 含义 | 示例 |
|------|------|------|
| Work 核心字段 | 作品身份和最低必要信息 | title, synopsis |
| WorkMetadata | 写作参照面板字段 | tags, theme, conflict, style |
| WorkChapter | 章节结构字段 | chapterNumber, title, synopsis |
| WorkBody | 正文字段 | chapter.content |
| FlowState | 流程状态字段 | status, release timestamps, deletedAt |
| Legacy/Frozen | 1.0 或 AI 遗留，不进入新设计 | masterPrompt 等 |

### 4.2 初步治理判断

以下只是初步分类，需 Hermes 做本地代码和文档审计后确认：

| 现有名 | 初步归类 | 说明 |
|--------|---------|------|
| `Project.title` | Work 核心字段 | 对应作品标题 |
| `Project.description` | Work 核心字段候选 | 可能对应作品梗概，需与 metadata.synopsis 合并判断 |
| `Project.metadata` | WorkMetadata | 当前混合字段，需要拆解语义 |
| `Project.tags` | WorkMetadata | 可保留为标签 |
| `Project.wordCount` | 统计字段 | 不属于内容决策核心 |
| `Project.status` | FlowState | 流程状态，不属于作品内容 |
| `Project.masterPrompt` | Legacy/Frozen | AI 遗留字段，暂不进入内容模型 |
| `Chapter.title` | WorkChapter | 章节名 |
| `Chapter.summary` | WorkChapter | 章节梗概 |
| `Chapter.content` | WorkBody | 章节正文 |
| `Chapter.status` | Chapter FlowState | 章级状态，不等于 Work 流程状态 |

## §5 命名治理

### 5.1 产品与文档命名

必须使用：

- Work / 作品
- WorkDetailPage / 作品详情页
- 作品元数据
- 作品章节
- 作品正文

避免作为新设计口径使用：

- Project / 项目
- 项目详情页
- 设定页作为总称
- 元数据 Tab 作为不加解释的独立概念

### 5.2 代码迁移命名

短期允许：

- `Project` 作为 Prisma model 名。
- `projectsApi` 作为兼容 API 名。
- `projectId` 作为旧外键名。

但新增代码应优先引入语义别名：

- `type Work = Project`
- `workId` 作为前端变量名和路由语义名
- `worksApi` 作为 `projectsApi` 的兼容包装或未来替代入口

## §6 迁移策略

### P0：语义冻结

- 设计文档和 UI 文案统一使用 Work / 作品。
- `Project` 标注为 Legacy 技术名。
- 作品详情页三分法成为内容决策唯一口径。

### P1：本地审计

- 审计 Prisma schema 中 `Project` 字段。
- 审计前端 `Project` 类型、`projectsApi`、`WorkDetailPage`。
- 审计 `/work/:id` 入口与 `Project` 数据的对应关系。
- 输出字段归类表和迁移建议。

### P2：前端别名层

- 新增 `Work` 类型别名或 adapter。
- WorkDetailPage 只消费 Work 语义数据结构。
- 将旧 `Project` 字段映射到 `work.metadata / work.chapters / work.body`。

### P3：API 兼容层

- 保留 `projectsApi`，新增 `worksApi` 或语义 wrapper。
- 新代码调用 Work 语义接口。
- 旧接口逐步迁移，不一枪切断。

### P4：数据库迁移评估

只有在本地功能和 VPS 同步稳定后，再评估是否将 Prisma `Project` 重命名为 `Work`。

此步骤风险高，必须单独审计、备份、迁移和验证。
