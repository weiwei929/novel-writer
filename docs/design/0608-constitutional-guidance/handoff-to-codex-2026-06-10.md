## 一、项目现状共识

### 1.1 已知

- novel-writer 是 **React + Fastify + Prisma + SQLite** 全栈小说创作工具
- 后端完整 REST API（端口 5000），数据模型覆盖 Project / Chapter / Character / Timeline / CreativeFlow / Proposal / Scrap 等
- 前端五部门（创意组→企划课→创作室→编审部→文集库）基本框架已就位
- 0608 宪法级指引系列文档是唯一设计依据（旧 `overall-architecture.md` v4.1.1、`day1-design.md` 等已标记替代）

### 1.2 冻结

- **novel-writer 自带的 AI 路由（`/api/v2/ai/*`）保持冻结。** 这些是 v1.0 遗留，与 0608 五部门模型未对齐，从未被宪法级指引覆盖。不动、不改、不启用。
- Hermes 小说助手将承担 AI 层的角色，通过 API 驱动 novel-writer 数据，而非替换或修改后端 AI 路由。

## 二、创意组完整链路（补充 0608 设计空白）

### 2.1 原有问题

0608 模型对创意组的定义过于笼统——"灵感碎片、素材导入、创意形成、提案产出"，缺失了最关键的中游加工环节。

### 2.2 补充后的三层模型

```
创意组
═══════════════════════════════════════════

📥 素材层（三个来源，只读引用）
  ├ 外来参考 (FileReference)  — 外部文章、资料
  ├ 灵感碎片 (Scrap)          — 随手捕捉的想法片段
  └ AI 搜索                   — 前端 Tab，TASK-101/102 已交付

💬 进行中: 创意构思中 (CreativeFlow)
  作者引用素材，进行构思讨论。
  实体已建模，只需前端改标题："创意讨论"→"创意构思中"。
  可反复迭代，未完成前 = 构思中。

📋 已完成: 提案停留 (Proposal, status=created)
  从构思中提炼成型。
  列表呈现。每个条目内三选一。

═══════════════════════════════════════════
        三选一节点（提案停留条目上）
═══════════════════════════════════════════
  ✅ 提交企划课   → 触发企划课"待处理"队列
  📂 暂存         → Proposal.deletedAt = now（软删除，合规）
  ↩ 退回构思     → created → creating（部门内退回，合规）
```

### 2.3 素材类型区分

当前 `Scrap` 模型不区分"创意组灵感碎片"和"创作室灵感笔记"。建议新增 `source` 字段：

| source 值 | 含义 |
|-----------|------|
| `creative` | 创意组灵感碎片 |
| `studio` | 创作室灵感笔记 |
| (null) | 存量兼容 |

## 三、"只增不减"原则

### 3.1 三层约束

| 层级 | 规则 | 适用对象 |
|------|------|---------|
| **不可变核心** | 创建后不删不覆盖。可追加备注。 | 作品标题、立项梗概、Proposal 源 |
| **可追加字段** | 可新增条目和补充内容。不删已有条目。 | 角色列表、章节列表、时间线条目 |
| **可自由编辑** | 可随意改内容，可删除。 | 章节正文、灵感笔记、讨论记录 |

### 3.2 对 Hermes 的行为约束

```
Hermes 永远不能:
  ❌ 删除角色
  ❌ 覆盖核心梗概
  ❌ 删除已立项的章节
  ❌ 修改已提交 Proposal 的核心内容

Hermes 可以做:
  ✅ 新增角色，补充角色详情
  ✅ 追加设定段落
  ✅ 新增章节，修改章节正文
  ✅ 追加备注和讨论记录
```

## 四、交互层级分离（UX 宪法）

### 4.1 最高原则

> 流程决策的对象是该状态下列表中的某个条目。
> 内容决策的对象是作品详情页的内容。
> 两者区隔，互不交叠。

### 4.2 三层定义

```
Tab               → 只筛选、只展示。永远无操作按钮。
条目列表          → 流程决策。按钮决定条目下一步去向。
                   操作结果：条目在列表间移动。
详情页 / 编辑器   → 内容决策。只有保存。无阶段转换按钮。
                   操作结果：内容变化。条目位置不变。
```

### 4.3 两个维度对比

| | 流程决策 | 内容决策 |
|---|---------|---------|
| 对象 | 列表中的条目 | 详情页的内容 |
| 问题 | "这个条目下一步去哪？" | "这个内容够不够好？" |
| 动作 | 提交/放行/退回/暂存 | 保存/编辑/补充 |
| 结果 | 条目在列表间移动 | 内容变化，条目不移动 |
| 位置 | 只在列表页 | 只在详情页 |

### 4.4 五部门按钮映射（完整）

#### 创意组
| Tab | 按钮 |
|-----|------|
| 创意构思中 | [继续构思] [提炼为提案] |
| 提案停留 | [✅ 提交企划课] [📂 暂存] [↩ 退回构思] |

#### 企划课
| Tab | 按钮 |
|-----|------|
| 待处理 | [📥 接收入企划课] |
| 进行中 | [📝 完善作品规划] [✅ 完成企划] |
| 已完成 | [🚀 放行创作室] [↩ 退回规划] [📂 暂存] |

#### 创作室
| Tab | 按钮 |
|-----|------|
| 待处理 | [✍️ 开始创作] |
| 进行中 | [✍️ 继续写作] [🏁 作品已完成] |
| 已完成 | [🔍 提交审阅] [↩ 退回写作] [📂 暂存] |

#### 编审部
| Tab | 按钮 |
|-----|------|
| 待处理 | [🔍 开始审阅] |
| 进行中 | [🔍 继续审阅] [✅ 审阅完成] |
| 已完成 | [📚 文集入库] [↩ 退回审阅] [📂 暂存] |

#### 文集库
| Tab | 按钮 |
|-----|------|
| 待处理 | [📚 归库] |
| 已归档 | [👁 查看] [📥 导出 Markdown] |

### 4.5 详情页约束

```
详情页永远不出现:
  ❌ "提交企划课" / "完成企划" / "开始写作"
  ❌ "作品已完成" / "放行创作室" / "文集入库"
  ❌ 任何状态下拉框

详情页只有:
  ✅ [保存] — 内容修改
  ✅ 编辑器内 [保存并标记当前章完成] — 章级标记，不改变 Project.status
```

## 五、五部门现有不足诊断

| # | 问题 | 影响 |
|---|------|------|
| D-001 | 过于线性，违背迭代创作现实 | 写作中发现设定问题需切页面 |
| D-002 | "确认≠放行"对单人增加摩擦 | 两次操作完成一件事 |
| D-003 | 编审部只有空壳 | AI 审查能力未实现（恰好是 Hermes 强项） |
| D-004 | 文集库过于单薄 | 无导出格式、无排版 |
| D-005 | 为按钮设计，非为对话设计 | 端点语义和对话意图间有 gap |
| D-006 | 缺乏"当前作品"概念 | 多作品并行需反复指定 |
| D-007 | 灵感入口太深 | Scrap 埋在创作室侧栏 |
| D-008 | 缺少写作进度激励 | 无字数目标、完成率 |
| D-009 | 缺少修订轮次 | 退回不保留历史 |

## 六、Hermes 小说助手架构（预研，不阻塞 novel-writer）

### 6.1 定位

- Hermes = novel-writer 的 AI 层替代（取代冻结的 `/api/v2/ai/*`）
- 通过 REST API 驱动数据，novel-writer 前端只做展示
- 独立 Hermes profile（`novelist`），与开发 profile 隔离

### 6.2 三模式 + 横跨层

```
🌱 构思模式  →  素材收集 + 创意构思中 + 提案停留
📋 企划模式  →  元数据 + 角色工坊 + 章节架构
✍️ 创作模式  →  逐章协作 + 设定侧栏 + 灵感侧录
🔍 审阅模式  →  全书分析 + 一致性检查 + 归档导出

🔖 横跨层:  /灵感  /当前  /进度  /设定  /切换
```
