## §0 一句话总结

**"文件暂存" = 全局 L1 入口 = `Project.deletedAt` 软删机制**

**关键决定（2026-06-05 拍板 方案 C）**：
- **取消** `Project.status='shelved'` 主动暂存机制
- 文件暂存 = **只** 软删（`Project.deletedAt != null`）
- 理由：shelved 与软删 restore 行为完全一致（都是"回到原 status"），差异仅在用户触发时的意图——而这是 UI 文案层面，不需 2 套底层字段承载
- 字面量：9 primary + 3 legacy read（移除 shelved，从 10 → 9 primary）

## §2 涵盖范围

### 2.1 软删机制

- **触发**：`POST /projects/:id/soft-delete` → `Project.deletedAt = now`
- **状态机**：**不**改变 `Project.status`（保留原 status）
- **可触发状态**：**任何**状态（v4.1 §0 不变量："任何状态都可'删除'到全局文件暂存"）
- **恢复**：`POST /projects/:id/restore` → `deletedAt = null`，**status 保持**
- **永久删除**：文件暂存中可二次确认物理 DELETE

### 2.2 与 shelved 旧设计的对比（已废弃）

| 维度 | shelved 旧设计（已废弃）| 软删（v2 唯一机制）|
|------|-------------------------|---------------------|
| 字段 | `Project.status='shelved'` | `Project.deletedAt` |
| 状态机影响 | **改** status | **不**改 status |
| restore 行为 | status 恢复 | status 保持 |
| 永久删除 | 允许 | 允许 |
| UI 标识 | ⏸️ 暂停 | 🗑️ 软删 |
| 触发按钮 | "📥 暂存" | "📂 放入文件暂存" |
| 状态机纯净 | **破坏**（改 status）| **不**破坏（用 deletedAt 字段）|

**为什么取消 shelved**（方案 C 决策理由）：

1. **restore 行为一致**：shelved restore = `status = previousStatus`；软删 restore = `status 保持`。**两者完全等价**——都是回到 shelve/软删前的 status
2. **状态机纯净**：shelved 改 status（`planned → shelved`），跨阶段时（如 `shelved → writing`）需 M2 明确触发条件；软删用 deletedAt 字段，与状态机**解耦**
3. **archived 终态保护**：选项 B 的 shelved 设计让 `archived → shelved` 跨阶段，破坏终态语义；软删**不**破坏
4. **实现简单**：1 套机制 / 1 套端点 / 字面量 10 → 9 / 不需 M2 新增端点
5. **UI 不反直觉**：触发按钮文案"📂 放入文件暂存"明确归宿，二次确认强调"可随时恢复"

### 2.3 shelved 端点（M2 TASK-216）取消

- ~~`POST /projects/:id/shelve`~~ **取消**
- ~~`POST /projects/:id/restore-shelved`~~ **取消**
- M2 TASK-216 移出 backlog 或改为"增强文件暂存 UI" 议题

## §4 UI 文案（Day 2 决议 方案 C-2）

### 4.1 触发按钮文案

**位置**：各 L1 详情页（创作室/企划课/编审部/文集库/创意组）右上角"删除"位

**按钮文案**：

```
┌──────────────────────┐
│  📂 放入文件暂存      │  ← 主按钮（短、明确归宿）
└──────────────────────┘
```

**为什么不用"删除"**：
- "删除"对用户心理压力大
- "删除"暗示"不可恢复"，与"软删可恢复"事实不符
- "放入文件暂存"明确归宿 + "文件暂存"中性词

**为什么不用"暂存"**：
- shelved 旧设计叫"暂存"，混用会与 v4.1 字面量混淆
- "暂存"字面意思不清晰——用户不知道"暂存"会去哪

**为什么不用"中止"**：
- "中止"专业但用户不知道去向
- "中止"像临时状态（"我先中止一下"），与"软删"语义不匹配

### 4.2 二次确认弹窗

```
┌──────────────────────────────────────┐
│ 放入文件暂存？                        │
│                                      │
│ 此作品将进入文件暂存，可随时恢复。      │
│                                      │
│              [取消]  [确认放入]         │
└──────────────────────────────────────┘
```

**关键文案元素**：
- "放入文件暂存？" — 动作问句（与按钮一致）
- "可随时恢复" — **核心安抚文案**（打消用户"会不会删了就没了"顾虑）
- **不**写"将删除此作品"（避免"删除"措辞）

### 4.3 文件暂存页项目卡片

```
🗑️ 软删于 06-03 · 原状态：archived
   [查看]  [♻️ 恢复]  [🗑️ 永久删除]
```

**说明**：
- 显示"软删于 XX" + "原状态"（强调可恢复，status 没变）
- **不**写"已删除"（避免"删除"措辞）
- 永久删除按钮仍用 🗑️（与"软删"区别——物理删除）

### 4.4 文案差异对照

| 场景 | 旧措辞（v4.1 墓园）| 新措辞（v2 方案 C）|
|------|-------------------|-------------------|
| 触发按钮 | 🗑️ 删除 | 📂 放入文件暂存 |
| 弹窗标题 | "确认删除？" | "放入文件暂存？" |
| 弹窗副文 | "此操作不可撤销"（错）| "可随时恢复" |
| 项目卡片 | "墓园（3）" | "📂 文件暂存" |
| 项目状态 | "已软删" | "软删于 06-03" |
| 永久删除 | 🗑️ 永久删除 | 🗑️ 永久删除（不变）|

## §5 行为对照（恢复 vs 永久删除）

### 5.1 恢复行为

- **API**：`POST /projects/:id/restore`
- **变更字段**：`Project.deletedAt = null`
- **status 变更**：**不**变（保持原 status）
- **L1 入口**：项目从文件暂存消失，回到原 L1 入口（如 archived → 文集库）

### 5.2 永久删除

- **API**：`DELETE /projects/:id`
- **物理删除**：`DELETE FROM Project WHERE id = ?`
- **二次确认**：弹窗："确认永久删除？**不可恢复**"
- **关联数据**：章节/设定/心流等 CascadeDelete

### 5.3 与 v4.1 §0 不变量的一致性

v4.1 §0 "文件暂存规则" 全部适用：

- ✅ 挂全局（不分阶段）
- ✅ 软删除（`deletedAt`）
- ✅ 恢复保留原 status
- ✅ 永久删除（二次确认）
- ✅ 留作遗迹（看到就够了，不一定要恢复）

## §8 与跨阶段不退回原则的关系

### 8.1 文件暂存 ≠ 状态机回流

- **软删**：deletedAt 字段机制**不**是状态机，**不**破坏跨阶段不退回
- 软删 restore = `deletedAt = null`，**status 保持**（**不**流转）

### 8.2 跨阶段不退回的边界

- **软删** = **不**破坏（机制外，跨阶段不退回保持纯净）
- `archived` Project 仍**可**软删（v4.1 §0 不变量），但软删 restore 后**仍**是 `archived`（**不**回流到 writing/written）
