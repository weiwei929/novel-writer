## §0 文档元信息

- 版本号、日期、维护人
- 术语（冻结 = 不再作为下一阶段开发依据；停止写入 = 不再产生新的该类型数据；LEGACY_READ = 存量数据保留但不再新增）
- 冻结层级：
  - **L1 宪法级**：违反 0608 核心原则（跨部门退回、shelved、reject），任何例外需司令部书面批准
  - **L2 设计口径级**：v4.1 旧设计文档中的过时口径，不再引用，但不直接涉及用户路径
  - **L3 代码级**：前端/后端代码中的具体实现，逐步迁移替换

### §0.1 Legacy 默认无效原则

自 0608 修正案确立后，1.0 遗留项不再享有默认合法性。

治理判断从：

```text
能沿用就沿用
```

改为：

```text
所有 1.0 术语、字段、组件、API、页面入口必须重新举证。
不能证明符合 0608 宪法、流程/内容决策分离、Work 核心模型的，默认进入冻结、改名、迁移或删除候选。
```

这不是立即物理删除所有旧代码，而是取消 1.0 作为产品设计和领域模型的继承权。存量代码和数据只能作为兼容载体继续存在，并接受分阶段审计。

### §0.2 Legacy 治理分类

| 类别 | 判断标准 | 默认处理 |
|------|----------|----------|
| 语义污染 | 术语或 UI 文案与 0608 领域模型冲突 | 改名、废弃或冻结 |
| 功能可复用但命名旧 | 实现仍有价值，但暴露的是 1.0 名称 | 保留实现，新增 Work / 0608 语义 wrapper 或 adapter |
| 数据可能有价值 | 存量字段承载用户内容或历史上下文 | 不直接删除，兼容读取、迁移、标注来源 |
| 流程模型冲突 | 混合流程决策与内容决策，或跨部门越权 | 冻结用户路径，移回正确位置 |
| AI / 自动化遗留 | 1.0 AI 路由、prompt、自动化字段未被 0608 覆盖 | 冻结隔离，不进入当前主线 |

### §0.3 典型新增审查对象

以下对象不一定立即删除，但必须进入 Legacy 复核：

- `Project` 作为产品语义、UI 文案或新增类型命名。
- `章节规划`、`章节管理` 等 1.0 后台管理式命名。
- `Project.description` 与 `metadata.synopsis` 的双梗概来源。
- `masterPrompt` 及 1.0 AI 辅助字段。
- `/projects/*` 中继续承担 Work 语义的新调用。
- 任何绕过“编辑作品详情”强指令的内容编辑入口。

## §1 L1 冻结项（宪法级）

### F-001：跨部门退回

| 维度 | 值 |
|------|-----|
| **冻结对象** | 任何跨部门退回的按钮、文案、API 调用、流程解释 |
| **冻结范围** | 前端 UI、后端端点、API 签名、设计文档、README |
| **冻结原因** | 0608 §3.3"不允许跨部门退回"。部门 B 不能否决部门 A 的决定。跨部门争议走文件暂存池。 |
| **取代方案** | 部门内退回（`planned→planning`/`written→writing`/`reviewed→reviewing`）+ 文件暂存池线外裁决 |
| **迁移状态** | ❌ 未开始 |

**禁止示例**：

```
企划课 → 退回创意组          ❌
创作室 → 退回企划课          ❌
编审部 → 退回创作室          ❌
在 StageTransitionModal 中     ❌ （PREV_STATUS: writing→planning 等）
proposalsApi.reject() 用户路径 ❌
```

**仍允许**（部门内部退回）：

```
planned → planning       ✅ 企划课内部退回设定中
written → writing        ✅ 创作室内部退回写作中
reviewed → reviewing     ✅ 编审部内部退回审阅中
```

### F-002：reject 用户路径

| 维度 | 值 |
|------|-----|
| **冻结对象** | `reject` 作为用户可见的前端路径 |
| **冻结范围** | 前端按钮、UI 文案、用户流程 |
| **冻结原因** | reject 是跨部门退回的另一种形式（"创意组提案 → 创意组退回"是跨部门退回的变体），违反 0608 §3.3 |
| **取代方案** | 不接收 = 放入文件暂存（`deletedAt`），**不是退回到创意组** |
| **迁移状态** | ❌ 未开始 |

**注意**：后端 `reject` 历史端点可暂时保留（转为 internal/legacy 标记），但禁止再作为用户可见流程接入。

### F-003：shelved 字面量（用户路径）

| 维度 | 值 |
|------|-----|
| **冻结对象** | `status: shelved` 作为用户可见暂存路径 |
| **冻结范围** | 前端 UI（按钮/标签/筛选）、新写入数据库 |
| **冻结原因** | 0608 §4 + 会诊结论 §5.3：文件暂存优先使用 `deletedAt` 机制。shelved 与软删机制重复，且引入 `shelved → writing` 等跨阶段流转风险 |
| **取代方案** | `deletedAt != null` 作为文件暂存唯一标记。恢复时清除 `deletedAt`，回到原 status 所属队列 |
| **迁移状态** | ❌ 未开始。后端 `shelved` 仍为 PRIMARY，待数据审计后移入 LEGACY_READ |

**紧急行动**（New Commit 1 前）：
- 前端所有 `shelve` 按钮 → 替换为 "📂 放入文件暂存"（调用 soft-delete 而非 shelve）
- `status: shelved` 不应出现在 UI 下拉/筛选器中

### F-004：全局线性 NEXT/PREV 阶段推进器

| 维度 | 值 |
|------|-----|
| **冻结对象** | `NEXT_STATUS` / `PREV_STATUS` 自动生成阶段按钮的模式 |
| **冻结范围** | `StageTransitionModal.tsx` 的全局线性链路逻辑 |
| **冻结原因** | 0608 §3 + 会诊结论 §5.5：阶段按钮不应由全局 N→N+1 链决定，而应由"当前部门 + 当前工作区 + 当前 status + 用户意图"共同决定 |
| **取代方案** | 每个部门有自己的一组操作按钮，按当前部门上下文和工作区渲染。按钮不是从一个全局的"下一个状态"表中推导的 |
| **迁移状态** | ❌ 未开始。StageTransitionModal.tsx 含有跨部门退回（F-001）和线性推进（F-004）两类冻结 |

## §2 L2 冻结项（设计口径级）

### F-005：v4.1"三选一节点"混合语义

### F-007："正式立项"文案

| 维度 | 值 |
|------|-----|
| **冻结对象** | 企划课中"正式立项"的按钮文案和语义 |
| **冻结范围** | 前端 UI、设计文档 |
| **冻结原因** | 会诊结论 §8.2："planning → planned 文案改为'确认企划完成'"。"正式立项"隐含"已完成企划 → 自动开始创作"的联通 |
| **取代方案** | "确认企划完成"（部门内确认）+ "放行至创作室"（跨部门放行，在 Tab ④ 完成） |
| **迁移状态** | ❌ 未开始 |

### F-008："一键进入编辑器"流程

| 维度 | 值 |
|------|-----|
| **冻结对象** | `planned → startWriting → navigate(editor)` 的"确认完成=放行=开始写作"三合一流程 |
| **冻结范围** | 前端路由跳转、用户流程 |
| **冻结原因** | 会诊结论 §3（Cursor 回报采纳）：混淆了"放行创作室"和"开始写作"。0608 模型要求放行≠开始写作。企划课放行后作品进入创作室待处理队列，由创作室独立决定何时开始写作 |
| **取代方案** | "放行至创作室" → 停留在当前视图 + toast 提示。"开始写作"是创作室待处理列表中的独立动作 |
| **迁移状态** | ❌ 未开始 |

### F-009：`planned` -> `writing` 的直接端点

| 维度 | 值 |
|------|-----|
| **冻结对象** | 从企划课 Tab ④/作品详情页直接调用 `planned → writing` |
| **冻结范围** | 前端按钮、后端端点调用路径 |
| **冻结原因** | 同上 F-008。放行（企划课动作）和开始写作（创作室动作）必须分离 |
| **取代方案** | 放行端点不改变 status（保持 `planned`）；开始写作端点在创作室 L1 待处理列表中触发（`planned → writing`）|
| **迁移状态** | ❌ 未开始 |

## §5 冻结监控

### 5.1 如何新增冻结项

发现新的违反 0608 原则的代码路径/设计口径时，按以下流程新增：

1. 确认违反的 0608 原则（引用 § 编号）
2. 判断冻结层级（L1/L2/L3）
3. 写入本文件对应层级
4. 同步更新 `code-conflict-analysis.md` 中的对应冲突点标记

### 5.2 如何解除冻结

1. 提交解除申请（含：冻结项编号、解除理由、代替方案）
2. 司令部会诊确认
3. 更新本文件（状态改为"已解除"，注明解除日期和批准者）
4. 更新设计文档和代码

### 5.3 冻结版本快照

本文件 v1 对应 0608 集中会诊结论 v1（2026-06-08）。后续每次宪法级指引更新时，本文件应与新版本比较，重新验证所有冻结项的状态。
