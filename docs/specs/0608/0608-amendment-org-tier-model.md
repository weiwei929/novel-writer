## §0 修正案摘要

0608 既有模型把作品当作**工件**，描述了它如何在五部门间流动；但缺失了**谁在哪一层做事**这一维度。本修正案补上该主梁：

> novel-writer 模拟一个**三层科层的小公司**：总经理 → 五个科层部门 → 部门员工。
> 虽为单人使用，但刻意按多人协作的组织场景建模。

两条定调（司令部 2026-06-11）：

1. **层级纯隐式**：不引入角色切换 UI、不引入用户/权限系统。层级只通过"当前在哪个工作区、点哪个按钮"体现。
2. **AI 做员工，人做管理**：Hermes 承担员工层的内容劳动；人只做主管/总经理层的管理决策。

---

## §1 三层科层定义

| 层级 | 角色 | 职责 | 决策类型 |
|------|------|------|---------|
| **员工层** | 各部门员工（由 Hermes 承担） | 在"进行中"工作区做内容劳动 + 确认完成 | 内容决策 |
| **主管层** | 部门主管/经理（由人承担） | 在"已完成"工作区做放行 / 退回 / 暂存 | 流程决策 |
| **总经理层** | 总经理（由人承担） | 跨部门总览 + 暂存池裁决 | 管理/裁决 |

五个科层部门（横向）：**创意组 · 企划课 · 创作室 · 编审部 · 文集库**。

### 1.1 层级与现有工作区的隐式映射

层级不显性出现在 UI，而是由"工作区 + 动作"隐式承载：

```
进行中工作区  ← 员工层主场（内容劳动 + 确认完成）
已完成工作区  ← 主管层主场（放行 / 退回 / 暂存）
跨部门总览页  ← 总经理层主场（负载、瓶颈、暂存池裁决）
```

约束：

- 不出现"切换为员工 / 主管 / 总经理"的视角开关。
- 不引入 `role` / `permission` 字段或登录账户。
- 用户始终是同一个人，扮演哪一层取决于他此刻在哪个工作区操作。

---

## §2 放行模型裁决：采用 A

`0608-audit-pipeline-handoff.md` §7-G1 的 A/B 选型，**正式裁决为 A**。

理由：三层科层中，"确认完成"与"放行"分属**员工层与主管层两个不同角色**的动作，是要刻意模拟的科层审批，不是单人摩擦。

| 动作 | 层级 | 工作区 | 语义 | 实现要求 |
|------|------|--------|------|---------|
| 确认完成 | 员工层 | 进行中 → 已完成 | 本部门员工收工 | 既有语义端点（如 `mark-written`）|
| 放行 | 主管层 | 已完成 → 下游待处理 | 主管把成品交给下一部门 | **需新增 `release-to-*` 端点 + 交接时间戳** |
| 退回（部门内）| 主管层 | 已完成 → 进行中 | 主管打回返工 | 桶内白名单需放开（如 `planned→planning`）|
| 暂存 | 主管层 | 任意 → 暂存池 | 主管搁置争议件 | `deletedAt`（既有 soft-delete）|
| 裁决 | 总经理层 | 暂存池 | 总经理处置搁置件 | 既有 restore + 暂存池视图 |

因此 `0608-audit-pipeline-handoff.md` 的修复方向锁定：

- **H03（三个假放行按钮）→ 补成真实放行端点**，不删按钮。
- **H04（放行门禁缺失）→ 下游列表按"已放行"过滤**，而非纯 status。
- **H01/H02（归档、退回企划报错）→ 放开对应转换 / 补端点。**

## §3 Hermes 边界：AI = 员工层

确立人机分工：

```
Hermes（AI 员工层）              人（主管 / 总经理层）
─────────────────────          ─────────────────────
在"进行中"工作区做内容劳动：     在"已完成"工作区做管理决策：
  · 创意构思、素材整理             · 放行 / 退回 / 暂存
  · 企划元数据、章节架构           · 跨部门总览
  · 写正文                         · 暂存池裁决
  · 审阅、批注、修订建议
  · 全书分析、导出排版
```

推论：

- novel-writer 自带 `/api/v2/ai/*` 保持冻结；AI 能力由 Hermes 经 REST API 驱动数据承担（与 handoff-to-codex 一致）。
- novel-writer 前端"进行中"工作区未来主要形态 = **看 AI 干活 + 下指令**。
- 人的主战场是"已完成"工作区与总览页——即管理层。
- Hermes 受"只增不减"行为约束（见 handoff-to-codex §三）：不删角色、不覆盖核心梗概、不删已立项章节。

**时序（Codex 复盘 2026-06-11 确认）**：

- **当前继续冻结 Hermes 与 `/api/v2/ai/*`。** novel-writer **先成为稳定的"人类工作台"**。
- Hermes 未来作为**外部执行者**接入，走与人**同一套 REST / 页面语义**工作；不让 novel-writer 后端自己长出 AI 自动化。
- 即：先把五部门流水线（含提交/门禁）跑通，AI 接入是其后的独立议题。

## §4 对既有 0608 原则的影响

| 原则 | 影响 |
|------|------|
| #2 确认完成 ≠ 放行 | **获得组织依据**：两步分属员工层与主管层，是科层审批，必须保留 |
| #3 禁止跨部门退回 | 不变；跨部门争议由主管暂存、总经理裁决 |

## §5 隐式约束（防止过度工程）

- ❌ 不做角色/视角切换 UI。
- ❌ 不做登录、账户、`role`、`permission` 字段。
- ❌ 不做审批工作流引擎。
- ✅ 层级仅通过"工作区 + 动作"隐式体现。
- ✅ 总经理层最多体现为**一个跨部门总览页**（可选，非 P0）。
- ✅ **文案分轨**：架构层/端点名用 `release`/`handoff`（交接事实）；**UI 用户文案一律用「提交」**（提交创作室/编审部/文集库），不用"放行"。

---

## §7 不变量

1. 系统模拟三层科层：总经理 → 五科层 → 员工，单人扮演全部。
2. 层级永不显性化为 UI 开关或权限字段。
3. 员工层 = AI（Hermes），管理层 = 人。
4. 确认完成（员工）与放行（主管）永不合并为一个动作。
5. 放行必须产生可审计的交接事实。
