## §0 修正案摘要

0608 原模型已经定义了五部门、三工作区、状态机和跨部门放行协议。本修正案补充一个更底层的不变量：

> **内容变化不等于流程推进。流程推进必须是独立、显式、可审计的动作。**

因此，novel-writer 中所有用户操作必须先归类为两种决策之一：

| 决策类型 | 核心问题 | 决策对象 | 发生位置 | 典型动作 |
|---------|---------|---------|---------|---------|
| 内容决策 | “这个内容怎么改？” | 作品、素材、设定、章节、批注 | 详情页 / 编辑器 / 内容表单 | 保存、编辑、补充、删除草稿 |
| 流程决策 | “这个条目下一步去哪？” | 部门列表中的某个条目 | 部门工作区列表 | 提交、接收、完成、放行、退回、暂存 |

两者可以互相提供依据，但不能在同一次隐式操作中混合。

同时，五阶段工作台必须坚持一个 UI 层不变量：

> **工作台不是页面集合，而是作品条目的操作场。**

创意组、企划课、创作室、编审部、文集库的工作台页面，只负责把作品条目按阶段、状态或来源组织起来。除创意组左侧“创意来源”这类素材入口外，工作台中的主要流程动作、内容入口和状态判断都应锚定到某个具体作品条目。

## §1 宪法级规则

### 1.1 内容决策规则

内容决策只改变内容，不改变流程位置。

允许：

- 在详情页保存作品元数据、角色、章节、时间线、批注。
- 在写作编辑器保存章节正文。
- 在审阅页保存审阅意见和问题记录。
- 在创意构思页保存讨论记录、素材引用和提案草稿。

禁止：

- 点击“保存”时隐式改变 `Project.status` 或 `Proposal.status`。
- 在详情页中出现“开始写作”“完成企划”“提交审阅”“文集入库”等阶段转换按钮。
- 用内容表单字段直接暴露或修改流程状态。

### 1.2 流程决策规则

流程决策只改变条目在部门工作区中的位置，或记录跨部门交接，不隐式改写内容。

允许：

- 在部门列表条目上点击“完成企划”“放行创作室”“开始写作”“提交审阅”“归库”。
- 在部门列表条目上执行部门内退回。
- 在部门列表条目上执行文件暂存。

禁止：

- 在执行流程推进时顺手覆盖正文、梗概、角色设定等内容。
- 在详情页、编辑器、Tab 导航中触发流程推进。
- 使用全局线性推进器推导下一状态。

### 1.3 Tab 规则

Tab 只负责筛选和展示。

禁止：

- Tab 点击触发状态改变。
- Tab 点击触发接收、放行、完成、退回、暂存。
- 在 Tab 本身放置流程动作按钮。

## §2 页面职责划分

### 2.0 UI 文案显性化

UI 文案应帮助用户区分“当前列表中的对象是什么”和“该对象是否允许内容写入”。

| 部门 | 列表对象名 | 工作区文案 | 内容决策开放态 |
|------|-----------|-----------|---------------|
| 创意组 | 创意作品 | 构思中 / 已完成 | 构思中 |
| 企划课 | 企划作品 | 待企划 / 企划中 / 已完成 | 企划中 |
| 创作室 | 创作作品 | 待创作 / 创作中 / 已完成 | 创作中 |
| 编审部 | 审阅作品 | 待审阅 / 审阅中 / 已完成 | 审阅中 |
| 文集库 | 文集作品 | 待归库 / 已归档 | 默认只读，导出和归档为流程动作 |

只有“构思中 / 企划中 / 创作中 / 审阅中”四个进行中状态允许进入详情页、编辑器或内容表单执行写入、修改、保存等内容决策动作。

其他状态下的详情页应默认只读；若需要修改内容，必须先通过列表条目上的流程决策回到对应进行中状态。

### 2.1 Tab

职责：

- 切换部门工作区或视图过滤条件。
- 改变列表展示范围。

不负责：

- 创建流程事件。
- 修改内容。
- 改变 `status`、放行标记或 `deletedAt`。

### 2.2 部门列表

职责：

- 展示当前部门、当前工作区下的条目。
- 承载流程决策按钮。
- 让用户明确决定条目下一步去向。

示例：

- 创意组“提案停留”列表：提交企划课 / 暂存 / 退回构思。
- 企划课“进行中”列表：完善作品规划 / 完成企划。
- 企划课“已完成”列表：放行创作室 / 退回规划 / 暂存。
- 创作室“进行中”列表：继续写作 / 作品已完成。

### 2.3 工作台条目锚点

职责：

- 工作台页面以作品条目为主要操作锚点。
- 流程按钮、状态移动、详情进入、内容编辑入口，应尽量出现在具体作品条目附近。
- 页面级说明区只解释当前模块职责、使用方式和统计概况，不直接承载流程决策。
- 三列工作台只负责组织条目，帮助用户一眼判断作品处于哪个阶段、下一步能做什么。

允许：

- 在作品条目卡片上显示“开始创作”“确认审阅完成”“提交文集库”等流程动作。
- 在作品条目卡片上进入作品详情页、正文编辑器或审阅页。
- 创意组左列保留“灵感碎片 / 外来参考 / AI 搜索”等来源摘要入口；但一旦进入作品主流程，后续决策必须落到作品条目上。

禁止：

- 用页面级全局按钮替代作品条目上的流程决策。
- 让用户先选择抽象功能，再反向寻找作品条目。
- 在没有明确作品条目锚点的情况下执行阶段推进、提交、退回、暂存。
- 把部门工作台退化为若干子页面链接集合。

### 2.4 详情页与编辑器

职责：

- 承载内容阅读、编辑、保存。
- 展示当前部门上下文下的内容视图。
- 为流程决策提供内容依据。

不负责：

- 推进项目阶段。
- 放行到下一部门。
- 修改流程状态。

## §3 与既有 0608 原则的关系

### 3.1 对“确认完成 ≠ 放行下一部门”的解释

“确认完成”和“放行下一部门”都是流程决策，但属于两个不同流程动作：

- 确认完成：本部门判断本阶段工作完成，条目进入本部门“已完成”工作区。
- 放行下一部门：本部门决定将已完成条目交给下一部门待处理。

二者不得合并为一个隐式动作。

### 3.2 对“部门上下文决定标签”的解释

流程语义发生在部门列表上下文中。同一 `status` 在不同部门可以有不同标签，是因为它在不同流程决策位置上承担不同含义。

例如：

- `planned` 在企划课列表中表示“企划已完成，等待放行”。
- `planned` 在创作室列表中表示“已放行到创作室，等待开始写作”。

### 3.3 对“拒绝全局线性推进器”的解释

流程按钮不能由全局 `NEXT_STATUS` / `PREV_STATUS` 推导。

正确推导条件必须至少包含：

- 当前部门。
- 当前工作区。
- 当前条目类型。
- 当前状态或放行标记。
- 当前用户意图。

### 3.4 对“文件暂存池”的解释

暂存是流程决策，不是内容编辑。

因此：

- 暂存按钮只应出现在列表条目操作区。
- 暂存使用 `deletedAt` 等元标记。
- 暂存不得改写作品正文、设定、提案核心内容。

## §4 审查清单

任何新 commit 涉及前端页面、状态按钮、保存动作或路由跳转时，必须检查：

- [ ] Tab 是否只筛选展示，不触发动作？
- [ ] 列表按钮是否只做流程决策？
- [ ] 详情页和编辑器是否只做内容决策？
- [ ] “保存”是否不会改变 `Project.status` / `Proposal.status`？
- [ ] 阶段转换按钮是否没有出现在详情页或编辑器？
- [ ] 流程推进是否没有隐式改写内容？
- [ ] 是否避免使用全局线性阶段推进器？
- [ ] 暂存是否作为列表条目流程动作实现？
- [ ] 工作台中的流程动作和内容入口是否锚定到具体作品条目？
- [ ] 页面级说明区是否只做解释和统计，不承载脱离作品条目的流程决策？
- [ ] 部门工作台是否避免退化为子页面导航集合？

## §5 实施影响

### P0：立即生效

- 新增或修改页面时，必须先判断操作属于内容决策还是流程决策。
- 详情页中已有阶段转换按钮应迁移到对应部门列表。
- Tab 不得承载任何状态改变。

### P1：与 `0608-ux-interaction-model.md` 联动

- `0608-ux-interaction-model.md` 负责把本修正案落到具体页面与按钮映射。
- 若具体按钮表与本修正案冲突，以本修正案为准。

### P2：后端端点语义对齐

- 内容保存端点不得顺带推进流程。
- 流程端点应使用显式业务语义命名。
- 放行端点应记录交接事实，不自动启动下一部门工作。
