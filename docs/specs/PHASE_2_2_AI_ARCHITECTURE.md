# Phase 2.2: AI 深度规划师与上下文管理设计规范

> **状态**: 草案 (Draft)
> **日期**: 2025-12-15
> **目标**: 确立“主客”交互模式，定义为了 Token 效率和生成质量的上下文分级策略。

## 1. 上下文管理策略 (Context Management Strategy)

这一策略的设计核心是 **"按需注入" (Injection on Demand)**，以节省 Token 并防止模型注意力涣散。

### Tier A: 核心元数据层 (High Priority)
*   **定义**: 作品的“灵魂”和“骨架”。
*   **包含内容**:
    *   **项目元数据**: 标题、类型、核心梗概 (Logline)、当前世界观设定 (Worldview)、核心人物表 (Character List)。
    *   **章节元数据**: 章节标题、本章摘要/目标 (Chapter Goal)。
*   **特性**:
    *   **始终存在**: 所有的 AI 请求（对话、写作、审阅）**必须**包含此层级。
    *   **等级最高**: AI 必须严格遵循此处的设定（如人物性格、世界规则）。
    *   **体积限制**: 严格控制，通过 UI 引导用户精简描述。

### Tier B: 章节作业层 (Working Context)
*   **定义**: 当前正在进行的创作环境。
*   **包含内容**:
    *   Tier A 内容。
    *   **当前章节正文**: 目前编辑器中的内容。
    *   **上文回顾** (可选): 前一章的摘要 (Previous Chapter Summary)。
*   **适用场景**: `AI 辅助写作` (续写、润色、头脑风暴)。
*   **限制**:
    *   **状态**: 视为“草稿”，不作为全局事实，直到用户确认为元数据。
    *   **体积**: < 5000 汉字。超过部分应截断或仅保留摘要。

### Tier C: 全局审阅层 (Global Context)
*   **定义**: 作品的全貌。
*   **包含内容**: 所有章节的完整内容或详细摘要。
*   **适用场景**: 仅用于 `AI 终稿审阅` (Final Review) 或 `全局逻辑检查`。
*   **触发**: 仅在用户显式点击“全书审阅”时触发，不参与日常写作。

## 2. 交互体验规范 (Interaction & UX)

遵循 **"作者为主，AI 为客" (Host-Guest Protocol)** 原则。

### 2.1 约束与边界
*   **元数据生成**: 单次不超过 1000 汉字。侧重结构化、条理性。
*   **辅助写作**: 单次不超过 300 汉字。防止 AI 抢夺创作权，保持作者的掌控感。
*   **对话交互**: 短小精悍，引导性提问。

### 2.2 "对话 -> 确认 ->以此为据" (Chat-Confirm-Commit) 工作流
这是核心的 **"构思 (Ideation)"** 流程。

1.  **Chat (发散)**: 用户与 AI 在对话框中讨论（如：“帮我构思一个反派的动机”）。
2.  **Select (决策)**: 用户从 AI 的回复中选中满意的部分，或者修改 AI 的建议。
3.  **Confirm (确认)**: 此时数据仅在对话历史中。
4.  **Commit (入库)**: 用户点击“**采纳为设定**” (Apply to Metadata)。
    *   系统将这部分内容写入 `Tier A` 元数据（如更新“人物小传”字段）。
    *   **一旦入库，即成为后续 AI 生成的“法律”**。

## 3. 实现计划 (Implementation Roadmap)

### 3.1 后端 (Backend)
*   **`ContextManager` 服务**:
    *   实现 `buildProjectContext(projectId)` (Tier A)。
    *   实现 `buildChapterContext(chapterId, currentContent)` (Tier B)。
*   **Prompt 模板优化**:
    *   将 System Prompt 拆分为 `Role` (角色), `Constraints` (约束/字数限制), `Knowledge` (Tier A 数据)。

### 3.2 前端 (Frontend)
*   **元数据面板 (Metadata Panel)**:
    *   提供可视化界面让用户编辑 Tier A 数据（不再是黑盒）。
*   **对话操作区**:
    *   在 Chat 消息下方增加快捷操作：`[提取为摘要]`、`[更新到人物卡]`。

---

## 4. 结论

这一分级策略**完全可行**，且非常必要。
*   **Token 优化**: Tier A/B 的分离避免了每次 API 调用都消耗巨量 Token。
*   **逻辑一致性**: 通过 Tier A 的强制注入，保证了 AI 不会“忘记”核心设定。
*   **创作主权**: 严格的字数限制和“确认入库”机制，确保了作者始终是驾驶员。
