## 四、新增能力：创作手记（编审部）

### 4.1 需求原文（司令官 2026-07-27）

> 在审阅部分增加一个「创作手记」：如实记录作品详情页中，除章节、正文之外的，作品设定中的「梗概、3+1」的内容，
> 最好能附带创建、修改的时间，相当于一个创作过程的时间线记录，**只记录**。

### 4.2 本质：创作过程记录（司令官 2026-07-27 三次澄清）

> 创作手记 = **创作过程记录**，从创意阶段开始，每一处决策都可回答「**为什么**」：
> 缘起——为什么有这个缘起？人物关系——为什么这么安排？时间场景——为什么是这样？
> 章节构建——为什么这么切？**尤其写作过程中的修改——为什么这么改？**
> 最后可写一篇总述性的「作品创作手记」，回顾来龙去脉，可长可短。

### 4.3 关键判断：记录与成形是两个时间点

司令官问：「只有在全文完成后，才会有这些记录，对吧？」——**对一半。**

| | 何时 | 内容 |
|---|------|------|
| **系统留痕** | 创意 → 企划 → 写作，**全程静默** | 改了**什么** |
| **手记成形** | **审阅阶段** | 为**什么**这么改 |

**要回答「为什么这么改」，必须先有「改了什么」的痕迹；而痕迹只能在改动发生的当下留下。**
数据库无历史表，`metadata` 只存当前值，改过即覆盖，事后无法补。

👉 **这就是记录层必须放在阶段一的原因** —— 不是着急，是它无法补做。

### 4.4 记录对象

| 显示名 | 数据键 | 说明 |
|--------|--------|------|
| 缘起 | Proposal `_creativeStage: 'origin'` | 立项时快照一次 |
| 梗概 | `metadata.synopsis` | |
| 人物与关系 | `workSetting.charactersAndRelations` | |
| 时间与地点 | `workSetting.timeAndPlace` | |
| 事件与情节 | `workSetting.eventsAndPlot` | |
| 叙事风格 / 创作心流 | `workSetting.narrativeStyle` | |
| **章节构建** | `metadata.chapterPlanning` | ⚠️ **推翻此前决定** —— 司令官三次澄清时明确要求纳入 |
| **总述手记** | `field='overview'` | 审阅阶段作者自由撰写，可长可短，单条可改 |

**不记录**：章节正文。

### 4.3 硬约束（必须先说清楚）

**数据库现无任何历史表。** `Project.metadata` 只存当前值，整行仅一个 `updatedAt`。
**过去改过什么、何时改的，一概不可查、不可重建。**

因此：**手记时间线只能从功能上线之日起算。** 这不是实现难度问题，是信息本身不存在。

> ### ⚠️ 设计收敛（司令官 2026-07-27 二次指示）
>
> **「自己保留」= 就在文集库里保留，不必过度理解。这只是过程记录，不需要做得像一个作品，粗糙点没关系。**
>
> 据此砍掉以下自加设计：两张表拆分、可见性/公开权限、diff 渲染引擎、导出成独立成文文档、双时间戳讲究。
> **以下 4.6 为最终设计；4.4 / 4.5 / 4.7 保留作设计推导记录，不作为实现依据。**

### 4.4 定位（司令官 2026-07-27 补充）

创作手记**不是一个查看面板，而是与作品并列的第二个产物**，随作品一同发布到文集库：

```text
《XXXX》作品        = 标题 + 章节 + 正文
《XXXX》创作手记    = 缘起 + 作品设定演变 + 修改及修改原因 + 写作幕后备注
```

这构成「**作品设定的完整闭环**」：设定不再只是写作前的输入，而是有来处、有演变、有理由的完整记录。

### 4.5 交互设计

**记录阶段（创意组 / 企划课 / 创作室）：完全隐性。**
系统静默记录，界面无任何提示，不打断创作。

**呈现阶段（编审部）：左右分栏。**

```text
┌─────────────────────┬──────────────────────┐
│   左栏：作品审阅     │   右栏：创作手记      │
│   （现有功能保留）   │   创作节点时间线      │
│                     │   ↓ 点击新增/修改点   │
│                     │   弹出备注框          │
│                     │   写「当时为什么改」   │
└─────────────────────┴──────────────────────┘
```

作者在审阅阶段回看整条创作轨迹，**在每个新增 / 修改点上点击，弹窗写入当时的理由或备注**——自动记录由此转化为真正的手记。

### 4.6 数据模型 —— 最终设计（一张表）

```prisma
model WorkNote {
  id         String   @id @default(uuid())
  projectId  String
  project    Project  @relation(fields: [projectId], references: [id], onDelete: Cascade)
  field      String   // origin | synopsis | charactersAndRelations | timeAndPlace
                      // | eventsAndPlot | narrativeStyle | chapterPlanning | overview
  content    String   // 当时的内容快照（overview 时即作者正文）
  note       String?  // 作者后补的「为什么」，可空、可改
  kind       String   @default("edit")  // edit | initial —— 见下方说明
  recordedAt DateTime @default(now())

  @@index([projectId, recordedAt])
}
```

**就这样。** 内容变了追加一条；编审部右栏按时间列出；点条目写 `note`；跟着作品进文集库。

**两处特例**：

- `field='origin'` —— 立项时把 Proposal 的 `_creativeStage: 'origin'` 内容快照一条，手记有个开头
- `field='overview'` —— 总述手记，审阅阶段作者自己写，`content` 即正文，全篇仅一条、可反复改

**`kind` 为什么必须有（2026-07-27 补，此前 §4.6 漏写导致与 §4.8 矛盾）**：

它区分的是**时间戳可不可信**。

| kind | `recordedAt` 的含义 | 可信度 |
|------|---------------------|--------|
| `edit` | 系统**亲眼看到**内容变化的那一刻 | ✅ 真实 |
| `initial` | 上线时对存量内容补拍的快照，**不是**作者写下它的时间 | ❌ 仅代表「开始记录的时间」 |

存量作品（如《美丽的一天》）的设定写于数周前，初始快照却会盖上上线当天的时间戳。
**无 `kind` 标记，这条记录即是谎言** —— 手记会显示「2026-07-27 创建了人物与关系」，而事实不然。
界面据此打出「初始快照 · 此前历史不可追溯」。

> **不采用「用 `note` 写固定文案」的替代方案**：`note` 是作者写「为什么」的空间，
> 混入系统文案会使人分不清哪句出自本人 —— 恰好毁掉本功能唯一在乎的区分。

`origin` 不是 kind，是 `field` 取值；立项记缘起属真实事件，`kind` 仍为 `edit`。

### 4.7 设计推导记录（不作为实现依据）

以下为收敛前的推导，保留备查：曾考虑拆「不可变快照表 + 可编辑批注表」以保住「只记录」的硬语义；曾要求右栏渲染 diff 以便回忆改动；曾区分 `recordedAt` / `annotatedAt` 双时间；曾设计导出为独立成文文档。**均已按司令官指示砍除**——过程记录不需要做成产品。

### 4.8 记录规则（已拍板）

| 决策点 | 结果 |
|--------|------|
| **记录粒度** | **内容一变就记**。与该字段最新一条内容相同则不重复记 |
| **存量作品** | **上线时做一次初始快照**，`kind='initial'`，标注「初始快照 · 此前历史不可追溯」 |
| **章节规划** | ✅ **进手记**（2026-07-27 三次澄清推翻初次决定，见 §4.4） |
| **记录阶段可见性** | **完全隐性**，仅编审部呈现 |

**写入实现要点**：

- 在后端 workSetting / synopsis 写入路径上**收口**（`PUT /projects/:id`、`confirm-metadata`、`applySynopsisMetadataWrite` / `pickWorkSettingPatch` 的全部调用点），统一走 `recordWorkNote(tx, projectId, before, after)`
- **务必先枚举全部写入点再动手**。遗漏一处即永久丢失该路径记录，且**不会报错**
- `content` 由系统写入；`note` 由作者填写，可改

### 4.9 发布到文集库

手记随作品进文集库，`LibraryDetailPage` 多一个「创作手记」入口即可。不做可见性区分，不做单独导出。

### 4.10 与 AI 冻结的关系

创作手记**完全不依赖 AI**。它恰好为当前被 AI 冻结掏空的编审部，提供了一个真实可用、且不可替代的能力。

## 四·五、通用纪律：验收数据不得污染真实创作资产

> **2026-07-27 补立。起因：两次实测。**
>
> - 700-A 侦察：新建了 4 条 `TASK700A-scout-*` 记录（已硬删，处理干净）
> - 700-G 验收：**直接修改了《美丽的一天》的 `charactersAndRelations`**，追加一行
>   `700-G 验收改动 2026-07-27T09:08:38.594Z`，未还原
>
> 后者性质更重：**改动既有真实数据，比新建测试数据难清理得多**，且会被创作手记如实记录下来——
> 作者的第一条真实创作记录，内容是一句测试文字。

**今后所有执行卡必须遵守：**

| # | 规则 |
|---|------|
| 1 | **验收优先使用临时作品**，不用真实创作资产（《美丽的一天》等）。临时作品标题带可识别前缀 |
| 2 | 若验收**必须**改动真实数据（如本例需产出 `kind=edit` 行），卡里**必须预先写明还原步骤**，回报中**必须确认已还原** |
| 3 | 一切验收残留（新建的行、改动的字段、写入的 note）**逐项列在回报里**，由司令官确认后再提交 |
| 4 | **参谋长出授权条时同样有责任**：要求"必须真实改数据"却不同时要求"改完还原"，是授权方的疏漏，不是执行方的违规 |

> **为什么不能靠事后 SQL 抹掉**：创作手记表是追加式的，直接删行等于伪造历史；
> 而通过界面还原会再生成一条记录——**难看，但真实**。宁可留下"改了又改回来"的痕迹，
> 也不要一份看着干净、实则被修饰过的记录。这是本功能存在的全部意义。
