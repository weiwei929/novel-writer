## §0 术语

| 术语 | 含义 |
|------|------|
| 作品构思中 | 创意组的"进行中"工作区。作者引用素材进行的结构化构思讨论。实体：`CreativeFlow`（只改前端标题，代码不动）。 |
| 提案停留 | 创意组的"已完成"工作区。已完成的 Proposal 以列表呈现，条目内三选一。 |
| 三选一节点 | 提案停留阶段的操作：✅ 提交企划课 / 📂 暂存（软删除）/ ↩ 退回构思（部门内退回）。 |
| 只增不减 | 作品设定的累积原则：核心不可变、条目可追加、正文可自由编辑。 |
| 横跨层 | Hermes 小说助手中跨越所有阶段的通用能力（灵感便签、上下文管理、进度看板）。 |

## §1 创意组完整链路（补全）

### 1.1 三层模型

```
创意组
═══════════════════════════════════════════

📥 素材层（三个来源，只读引用，不直接进入提案）
  ├── 外来参考 (FileReference)  — 外部文章、资料、参考文本
  ├── 灵感碎片 (Scrap, type=creative) — 随手捕捉的想法片段
  └── AI 搜索                    — 搜索结果（前端 Tab，TASK-101/102 已交付）

💬 进行中: 作品构思中 (CreativeFlow)
  作者引用素材，进行构思讨论。
  可关联多个素材，可反复迭代。
  未完成前 = 构思中。
  实体: CreativeFlow（已建模，前端标题改为"作品构思中"）。

📋 已完成: 提案停留 (Proposal, status=created)
  从构思中提炼成型。
  列表呈现，每个条目内三选一。
═══════════════════════════════════════════
              三选一节点
═══════════════════════════════════════════
  ✅ 提交企划课   → 触发企划课"待处理"队列
  📂 暂存         → Proposal.deletedAt = now（软删除）
  ↩ 退回构思     → created → creating（部门内退回，合规）
```

### 1.2 与 0608 冻结清单的合规检查

| 操作 | 涉及冻结项 | 合规性 |
|------|-----------|:---:|
| `created → creating`（退回构思） | F-001 跨部门退回 | ✅ 部门内退回，0608 §3.3 明确允许 |
| `提交企划课` | F-005 三选一混合语义 | ✅ 此处是 Proposal 层"放行"，不涉及 Project 状态 |
| `📂 暂存` | F-003 shelved | ✅ 走 `deletedAt` 软删除，不走 `shelved` 字面量 |

### 1.3 素材类型区分

**问题**：当前 `Scrap` 模型不区分"创意组灵感碎片"和"创作室灵感笔记"。二者语义不同——前者是创作前的素材，后者是创作中的侧录。

**方案**：Scrap 新增 `source` 字段（可选，存量兼容）：

| source 值 | 含义 | 使用场景 |
|-----------|------|---------|
| `creative` | 创意组灵感碎片 | 构思阶段捕捉的想法 |
| `studio` | 创作室灵感笔记 | 写作中的侧录、对话片段 |
| (null) | 未分类（存量兼容） | 旧数据 |

### 1.4 与现有设计的差异

| 维度 | 原 0608 设计 | 本补充 |
|------|-------------|--------|
| 创意组进行中 | 笼统描述"提案编辑中" | 明确为"作品构思中"，实体为 CreativeFlow |
| 素材→提案路径 | 未明确 | 素材 → 构思中(引用) → 提炼 → 提案 |
| 提案停留交互 | 未定义 | 列表 + 条目内三选一 |
| Scrap 语义 | 单一 | 区分 creative / studio 两种类型 |

## §2 "只增不减"原则

### 2.1 三层约束

| 层级 | 规则 | 适用对象 |
|------|------|---------|
| **不可变核心** | 创建后不可删除，不可覆盖。可追加备注。 | 作品标题、立项梗概、Proposal 源 (`proposalId`) |
| **可追加字段** | 可新增条目，可补充内容。不可删除已有条目。 | 角色列表、章节列表、时间线条目 |
| **可自由编辑** | 可随意修改内容，可删除。 | 章节正文（草稿）、灵感笔记、讨论记录 |

### 2.2 对数据模型的影响

| 实体/字段 | 当前行为 | 建议 |
|-----------|---------|------|
| `Project.metadata` | PUT 全量替换 | 建议支持 merge 语义（`$set` / `$append`），或拆分为独立字段 |
| `Character` | CRUD 均可 | 前端限制：只允许新增和编辑，隐藏删除按钮（或二次确认） |
| `Chapter` | CRUD 均可 | 保持不变。章节正文属于"可自由编辑"层 |
| `TimelineEntry` | CRUD 均可 | 前端限制：只允许新增和编辑 |
| `Proposal.innovation` / `synopsis` | 可编辑 | 已完成（created）后不可覆盖，只可追加 `sourceNotes` |

### 2.3 对 Hermes 的行为约束

这些约束写入 Hermes 的 persona/skill 作为硬性规则：

```
Hermes 永远不能:
  ❌ 删除一个角色
  ❌ 覆盖作品的核心梗概
  ❌ 删除已立项的章节
  ❌ 修改已提交的 Proposal 核心内容（标题/梗概/创新点）

Hermes 可以做:
  ✅ 新增角色，补充角色详情
  ✅ 在梗概基础上追加新设定段落
  ✅ 新增章节，修改章节正文
  ✅ 在 Proposal 上追加备注和讨论记录
  ✅ 新增时间线条目，补充已有条目
```

## §3 现有五部门流程的不足诊断

本诊断的目的是：**novel-writer 面向人类点击操作的流程，不能直接 1:1 映射为 AI 对话模式。** 需要做适配层。

### 3.1 结构性缺陷

#### D-001：过于线性，违背迭代创作现实

真实创作是高度迭代的。写第 10 章时发现第 3 章的伏笔有问题，需要同时改大纲、改角色设定、改正文。五部门"跨阶段不退回"（F-001）在数据模型层面是正确的，但在交互层面导致摩擦力。

**对 novel-writer 的影响**：创作者在创作室发现设定问题时，需要切到企划课页面修改，再切回创作室继续写作。

**化解方案**：在创作室的 WorkDetailPage 侧栏中，汇总显示所有已累积的设定（角色/时间线/元数据），并提供内联编辑入口，减少页面切换。

#### D-002："确认完成"与"放行"分离增加无意义操作

0608 的核心改进（F-005）将"确认完成"和"放行下一部门"分离。对多角色协作是正确的，但对单人创作者，两次操作完成一件事。

**对 Hermes 的影响**：对话中需要两轮确认，体验冗余。Hermes 可以将两步合并为一次确认提示（如"确认企划完成并放行创作室？"）。

#### D-003：编审部只有空壳

0608 中编审部被定义为"全文 AI 审查 + 非卡点 + prompt 驱动"，但当前实际落地只有前端 UI 框架（P3 已交付）。全书拉取、跨章节一致性检查、角色弧线追踪、节奏分析——这些核心能力未实现。

**对 Hermes 的影响**：编审部恰好是 Hermes + 大模型的最强项。Hermes 将承担编审部的实际 AI 能力，通过 API 读取全书数据进行分析，结果写入 Scrap 或 CreativeFlow 供作者参考。

#### D-004：文集库过于单薄

归档后没有导出格式选择（EPUB/PDF/TXT）、没有排版建议、没有封面文案生成。

**对 Hermes 的影响**：Hermes 可以在归档阶段提供这些辅助，通过 API 读取全书并生成多种格式。

### 3.2 交互适配缺陷

#### D-005：流程为"点击按钮"设计，非为"对话"设计

当前端点的语义（`POST /projects/:id/start-writing`）与对话意图（"我想开始写第三章了"）之间存在 gap。

**对 Hermes 的影响**：需要一个意图→API 的翻译层。Hermes 内置这个逻辑，将自然语言意图映射到正确的 API 调用序列。

#### D-006：缺乏"当前活跃作品"概念

多作品并行时，每次都需明确指定 projectId。对话中这很啰嗦。

**化解方案**：Hermes 维护"当前作品"上下文，自动注入 projectId。用户说"切换《深海猎人》"时更新。

#### D-007：灵感捕捉入口太深

Scrap 在创作室的侧栏中。灵感不分阶段——在企划课做设定时可能想到一段对话，在写作时可能想到一个新角色。

**化解方案**：提供一个横跨所有阶段的灵感入口。Hermes 侧用 `/灵感` 命令实现；前端侧在顶栏常驻一个快速捕捉入口。

### 3.3 创作体验缺陷

#### D-008：缺少写作进度与激励

没有每日字数目标、章节完成率、写作日历。

**对 Hermes 的影响**：Hermes 可以通过 API 拉取数据生成进度看板。不需要 novel-writer 改动。

#### D-009：缺少"修订轮次"概念

当前只有 `writing ↔ written`。没有第几稿的概念，退回不保留修订历史。

**对 Hermes 的影响**：暂不在 Hermes 中解决此问题。属于 novel-writer Day 3+ 的设计议题。

## §4 Hermes 小说助手架构

> **声明**：本节是预研性质。不要求 novel-writer 做任何对应改动。当 Hermes 小说助手正式构建时，本节作为设计依据。

### 4.1 核心原则

1. **Hermes 通过 novel-writer REST API 驱动数据**，novel-writer 前端只做展示层。
2. **novel-writer 自带的 AI 路由（`/api/v2/ai/*`）保持冻结**。它们与 0608 模型未对齐，属 v1.0 遗留。
3. **Hermes 遵循 novel-writer 的五部门状态机**，不做绕过状态机的直接数据库操作。
4. **Hermes 遵守"只增不减"原则**（§2.3 行为约束）。

### 4.2 三模式 + 横跨层

novel-writer 的五部门流程简化为 Hermes 的三个对话模式：

```
═══════════════════════════════════════════
  Hermes 小说助手 — 三模式 + 横跨层
═══════════════════════════════════════════

🌱 构思模式（创意组）
  ├─ 📥 素材收集: 存入 FileReference / Scrap / AI 搜索
  ├─ 💬 作品构思中: 苏格拉底式追问 → 写入 CreativeFlow
  └─ 📋 提案停留: 生成 Proposal → 三选一

📋 企划模式（企划课）
  承接 Proposal → 创建 Project(planning)
  ├─ 元数据补充（只增不减）
  ├─ 角色工坊（逐个深挖）
  ├─ 章节架构规划
  └─ 确认企划完成 → 放行创作室

✍️ 创作模式（创作室）
  承接 planned 作品
  ├─ 逐章协作: 读→讨论→写→写回
  ├─ 设定侧栏: 随时查看累积设定
  ├─ 灵感侧录: 随时捕捉想法
  └─ 完成确认 → 放行编审部

🔍 审阅模式（编审部 + 文集库）
  承接 written 作品
  ├─ 全书分析: 角色弧线 / 伏笔追踪 / 节奏
  ├─ 一致性报告 → 写入 Scrap / CreativeFlow
  └─ 归档 + 多格式导出

═══════════════════════════════════════════

🔖 横跨层（所有模式通用）
  /灵感 [内容]      → 随时存入 Scrap
  /当前             → 显示当前作品上下文
  /进度             → 字数 / 完成率 / 下一步
  /设定             → 快速查看累积的所有设定
  /切换 [作品名]    → 切换活跃作品
```

### 4.3 实现方式

#### novel-writer 侧（P1，创意组链路补全）

| 改动 | 范围 | 优先级 |
|------|------|:---:|
| "创意讨论"→"作品构思中" | 前端文案 | P4 |
| 创意组列表页显示 Proposal(created) | 前端 | P4 |
| 三选一按钮（提交/暂存/退回） | 前端 + 后端 | P4 |
| Scrap `source` 字段 | 后端 schema + 前端筛选 | P4 |
| Proposal 已完成状态保护 | 后端校验 | P4 |
| metadata merge 语义 | 后端 | P2 |

#### Hermes 侧（Day 3+，不阻塞 novel-writer）

| 组件 | 形式 | 说明 |
|------|------|------|
| `novelist` profile | Hermes profile | 独立配置：persona + 精简工具集 |
| `novel-writer-api` skill | Hermes skill | 封装 API 调用、认证、错误处理 |
| 构思模式 prompt 模板 | skill 内嵌 | 苏格拉底式追问、素材引用、提案生成 |
| "只增不减"约束 | persona.md | 硬编码行为规则 |
| 意图→API 翻译层 | skill 逻辑 | 自然语言 → API 调用序列 |
